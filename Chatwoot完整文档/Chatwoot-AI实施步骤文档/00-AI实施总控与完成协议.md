# AI 实施总控与完成协议

## 1. 总目标

AI 应首先依据 [全系统基础层规范](../Chatwoot全系统基础层规范/README.md)，再结合本目录和 00 至 48 功能基线分册，逐项完成 webchat 的功能补齐、合同统一、数据迁移、兼容验证和全系统验收。执行不能停留在方案说明，也不能只完成页面或单个接口；每个任务必须形成可使用、可验证、可恢复的完整业务闭环。

## 2. 权威信息顺序

出现冲突时按以下顺序判断：

1. [全系统基础层规范](../Chatwoot全系统基础层规范/README.md)的公共合同和零容忍规则；
2. 已冻结的目标版本、适用形态和不违反基础层的批准差异；
3. [模块化架构设计文档](../Chatwoot模块化架构设计文档/README.md)的边界、所有权、无环依赖和合同；
4. [日志基础层、审计与数据变更追踪设计文档](../Chatwoot日志审计与变更追踪设计文档/README.md)的强制采集、变更合同、不可变账本和覆盖矩阵；
5. 目标功能分册 00 至 42 的接口与业务规则；
6. webchat 补齐规范 43 至 48；
7. 本目录的实施顺序、任务状态，以及 29 至 32 分册的实际参数、第三方、拓扑和证据附件；
8. 既有系统当前行为。

既有行为与目标基线冲突时，不得静默保留；必须选择“调整为目标行为”或“登记为批准差异”。

## 3. AI 每轮执行循环

每一轮只选择一个最小可验收任务，按以下顺序执行：

1. 从 [总任务台账](01-总任务台账与依赖顺序.md) 和 [全任务状态记录](28-AI全任务状态记录.md) 找到第一个 `READY` 任务；
2. 阅读全系统基础层规范、任务所在分册、模块化架构约束、日志基础层约束、29 至 32 分册中适用的执行附件和它引用的功能基线；
3. 核对全部前置任务是否为 `DONE`，基础声明、模块边界、所有权、依赖和变更记录要求是否满足；
4. 记录任务开始时间、目标、影响对象、接口和验收案例；
5. 先确认现有能力属于保留、调整、新增还是替换；
6. 完成对象、业务规则、接口、权限、事件和异常处理；
7. 执行任务卡列出的正常、权限、重复、并发、失败和历史数据验证；
8. 核对列表、详情、实时事件、Webhook、报表、Local Change Journal 和集中审计副作用；
9. 登记结果、量化测量、第三方回执、拓扑结果、差异、证据索引和剩余风险；
10. 满足完成口径后改为 `DONE`，否则改为 `REWORK` 或 `BLOCKED`；
11. 重新计算被该任务解锁的后续任务；
12. 继续下一项，直到台账没有 `READY` 任务。

## 4. 状态定义

| 状态 | 含义 | 允许的下一状态 |
|---|---|---|
| PENDING | 任务尚未开始或依赖未完成 | READY、N/A |
| READY | 依赖满足，可立即实施 | RUNNING、BLOCKED |
| RUNNING | 当前正在实施 | VERIFYING、BLOCKED、REWORK |
| VERIFYING | 功能已形成，正在核对全部完成条件 | DONE、REWORK、BLOCKED |
| REWORK | 验收发现差异，需要修正 | RUNNING、BLOCKED |
| BLOCKED | 缺少凭证、外部条件、批准或数据 | READY、N/A |
| DONE | 全部完成条件和证据满足 | REOPENED |
| REOPENED | 因基线或关联能力变化重新打开 | RUNNING、BLOCKED |
| N/A | 经批准不适用于目标形态 | REOPENED |

AI 不得直接把 `PENDING` 改为 `DONE`，也不得把“尚未验证”解释为完成。

## 5. 单任务标准输出

每个任务结束时必须留下以下记录：

| 项目 | 必填内容 |
|---|---|
| 任务编号 | 分册内唯一编号 |
| 状态 | DONE、REWORK、BLOCKED 或 N/A |
| 基础层符合性 | foundation_version、接入声明、适用条款和验收结果 |
| 实施范围 | 本轮实际完成的功能边界 |
| 对象变化 | 新增或调整的对象、关系、状态和生命周期 |
| 接口变化 | 路径、方法、认证、字段、分页、错误和版本 |
| 权限变化 | 身份、角色、Inbox 范围、Feature 和套餐限制 |
| 副作用 | 事件、通知、Webhook、报表、审计和异步任务 |
| 验收结果 | 正常、异常、重复、并发、历史数据和跨入口结果 |
| 证据索引 | 请求结果、事件、数据快照、界面结果或第三方回执的位置 |
| 差异 | 与目标基线仍不同的内容及批准状态 |
| 后续任务 | 被解锁或需要重开的任务编号 |

## 6. 最小完整功能单位

功能不能被拆到失去业务意义。以下内容必须作为同一任务或同一任务组闭环：

- 创建对象与查询结果；
- 状态命令与状态变化后的事件；
- 第三方发送与最终送达或失败回执；
- 异步受理与最终完成、失败或取消；
- 权限允许与权限拒绝；
- 新入口与旧入口的相同业务结果；
- 主对象变化与报表、审计、通知、副作用；
- 删除动作与历史保留、脱敏或延迟清理。

## 8. 依赖处理规则

- 一个任务有多个依赖时，必须全部为 `DONE` 或批准的 `N/A`；
- 被阻断任务不阻止其他独立分支继续；
- 公共合同或主对象变化后，所有使用该合同的已完成任务必须标为 `REOPENED`；
- 渠道能力可以并行，但每个渠道必须独立通过完整闭环；
- AI Provider、插件和 Cloud 功能不得用模拟结果关闭“真实环境验证”任务；
- 迁移前必须冻结映射和唯一规则；迁移规则变化后必须重做受影响的对账；
- 任一权限边界变化后，相关功能的允许和拒绝案例必须重新验证。
- 模块边界、数据所有权、依赖方向或扩展点变化后，ARCH-01 至 ARCH-10 的受影响任务必须标为 `REOPENED`；
- 变更合同、敏感字段策略、保留策略、完整性规则或模块写入口变化后，LOG-01 至 LOG-08 的受影响任务必须标为 `REOPENED`；
- 基础层上下文、身份、对象、合同、API、安全、扩展或可靠性规则变化后，必须按基础层 09 分册重新分析影响并重开 ARCH、BAS、LOG、API、DATA、CONS 和 QA 的受影响任务；
- 任何数据写入都必须与 Local Change Journal 在同一原子边界完成，不能以集中账本暂时不可用为理由绕过本地记录；
- 任何功能任务不得以跨模块直接存储访问、重复权威数据或反向依赖作为临时完成方式。

## 9. 阻断处理

阻断记录至少包含：

- 阻断任务编号；
- 缺少的外部条件；
- 已完成的安全替代检查；
- 不解决阻断会影响哪些后续任务；
- 需要的决定或凭证；
- 可继续执行的独立任务；
- 最近一次复查时间。

仅仅“工作量大”“尚未轮到”或“还没有验证”不能标为阻断。

## 10. 差异处理

差异分为四类：

| 类型 | 处理 |
|---|---|
| 必须一致 | 未一致前任务不得完成 |
| 可归一化 | 验收时按冻结规则转换后比较 |
| 目标增强 | 保留增强能力，同时证明基线行为没有受损 |
| 批准差异 | 记录原因、影响、批准人、有效期和重新评估条件 |

缺少记录的差异一律视为失败。

## 11. AI 禁止提前结束的情况

存在以下任一情况时，AI 不得宣布全系统完成：

- 台账仍有适用的 PENDING、READY、RUNNING、VERIFYING、REWORK 或 REOPENED；
- BLOCKED 未被批准排除；
- 任何任务只有主流程证据，没有错误、权限或最终状态证据；
- 第三方渠道只有授权结果，没有真实消息闭环；
- AI 功能只有模型连接，没有知识、权限、额度和失败回退；
- 迁移只有总量相等，没有逐关系、抽样和新旧入口对账；
- 既有 webchat 能力出现回退；
- 长周期、并发、大数据量或套餐计费场景仍未关闭；
- 基线版本、Feature、Provider 版本或配置发生变化后未回归。
- 存在未登记写入口、无 change_id 的数据变化、未解决投递断层或敏感原值进入日志。

## 12. 全系统完成声明

只有 [25-全功能关门未决项清零与完成声明](25-全功能关门未决项清零与完成声明.md) 的全部条件为真，且 [32-全局证据包索引量化评分与完成台账](32-全局证据包索引量化评分与完成台账.md) 的零容忍项全部为 0，AI 才能生成完成声明。声明必须明确：版本、部署形态、容量档位、配置、Feature、第三方 Provider、适用和排除范围、验证日期、六项目标、量化结果、证据包位置、批准差异和下一次重验条件。
