# 统一对象、数据生命周期与迁移准备

> 批次：DATA，共 18 项。基线来源：03 至 06、09、10、14、16、34、40、43、44、48 分册，以及[统一对象规范](../Chatwoot全系统基础层规范/02-统一标识时间版本对象与生命周期.md)、[数据所有权与变更追踪规范](../Chatwoot全系统基础层规范/05-数据所有权原子一致性与变更追踪.md)和[目标架构](../Chatwoot模块化架构设计文档/10-可扩展简单实用可跟踪可量化可分可合目标架构.md)。

## 1. 目标

先确定全系统共享的对象、归属、唯一关系、状态、默认值和生命周期，再实施功能。每类权威数据只属于 26 个逻辑模块中的一个模块；组合部署不改变所有权，拆分迁移不改变业务语义。不得为不同渠道、接口、界面或部署形态建立彼此不一致的客户、会话和消息语义。

## 2. 任务清单

| 编号 | 对象或规则 | 实施步骤 | 关键关系与字段 | 完成判定 |
|---|---|---|---|---|
| DATA-01 | Account | 统一租户边界、时区、语言、设置、Feature、套餐和状态 | id、name、locale、timezone、settings | 所有业务对象可追溯到唯一 Account |
| DATA-02 | User 与成员关系 | 区分登录主体和 Account 成员关系 | user_id、account_id、role、status | 一个 User 可加入多个 Account 且权限独立 |
| DATA-03 | Team | 统一组织团队、技能组和分配组语义 | name、members、allow_auto_assign | Team 归属 Account，成员关系可审计 |
| DATA-04 | Inbox | 统一每条渠道入口、类型、成员、工作时间和健康状态 | channel_type、status、provider_config | 一条外部渠道映射唯一 Inbox |
| DATA-05 | Contact | 统一客户主体、标识、联系方式、公司和扩展属性 | identifier、email、phone_number | 同 Account 内唯一规则确定 |
| DATA-06 | ContactInbox | 统一客户在具体渠道中的身份 | contact_id、inbox_id、source_id | 同 Inbox 下 source_id 唯一 |
| DATA-07 | Company | 统一公司资料与联系人关系 | name、domain、industry、custom_attributes | 跨 Account 不共享公司对象 |
| DATA-08 | Conversation | 统一一次服务会话、显示 ID、状态、优先级和分配 | inbox、contact、contact_inbox、status | 必须同时关联客户和渠道身份 |
| DATA-09 | Message | 统一入站、出站、私有、活动和模板消息 | message_type、content_type、status、external_id | 必须属于会话并保留方向和发送者 |
| DATA-10 | Attachment | 统一文件、媒体、位置和转写信息 | file_type、size、url、status | 访问权限继承会话且可追踪安全状态 |
| DATA-11 | 运营对象 | 统一 Rule、RuleVersion、AutomationExecution、Macro、MacroVersion、MacroExecution、Campaign、Notification、SLA 和 Portal 归属；动作只引用已登记 Action Capability | account_id、inbox_id、capability_id、version、execution_id、status | 不允许跨 Account 绑定；规则、宏定义与执行记录可分别追踪 |
| DATA-12 | AI 与扩展对象 | 统一 Assistant、Document、Tool、App、Hook、Webhook 和 Bot 归属；区分扩展定义、安装实例、凭证引用、调用记录和用量 | account_id、assistant_id、installation_id、hook_id、invocation_id | 资源、凭证、调用和用量隔离，扩展不成为核心权威数据拥有者 |
| DATA-13 | 默认与空值 | 按 34 分册冻结创建默认、缺失、null、空字符串和空集合 | defaults、nullable、clear semantics | 创建和更新结果可预测 |
| DATA-14 | 唯一与标准化 | 冻结邮箱、电话、外部标识、时间和复合唯一规则 | normalized_email、phone、source_id | 重复和冲突结果明确 |
| DATA-15 | 状态与派生字段 | 区分可写状态、派生计数和时间字段 | status、last_activity_at、unread_count | 派生字段不能被普通入口直接伪造 |
| DATA-16 | 生命周期 | 定义创建、停用、软删除、脱敏、合并、解绑和延迟清理 | deleted_at、archived、merged_to | 每种对象删除后历史、事件和报表结果明确 |
| DATA-17 | 旧对象与模块拓扑映射 | 将 webchat 旧对象映射到统一对象，同时冻结拆分前后 owner_module、source_unit 和 target_unit | legacy_id、target_id、owner_module、source_unit、target_unit、mapping_status | 所有旧主对象和模块拆分、合并关系都有唯一映射策略 |
| DATA-18 | 数据与 Change 对账键 | 确定总量、关系、抽样、哈希、新旧入口和模块迁移对账使用的稳定键 | account_id、legacy_id、external_id、change_id、object_version、source_sequence、module_id | 迁移后可识别丢失、重复、错链、版本倒退和 Change 缺口 |

## 3. 模块数据边界

模块边界以[目标架构中的 26 个逻辑模块与数据所有权](../Chatwoot模块化架构设计文档/10-可扩展简单实用可跟踪可量化可分可合目标架构.md)为权威清单。本文件不重复定义第二份所有权表。每个模块必须建立以下四类数据目录：

| 数据类别 | 所有权与使用规则 | 拆分和合并要求 |
|---|---|---|
| 权威对象 | 仅 owner_module 可创建、校验和改变状态 | 迁移期间始终只有一个写入权威 |
| 外部引用 | 只保存稳定对象标识、必要显示快照和引用版本 | 不能以引用副本替代权威查询或命令 |
| Local Change Journal | 与权威对象变化原子产生，保存 change_id、object_version、module_id、correlation_id | 必须随模块一起迁移并连续对账 |
| 可重建投影 | 用事件或 Change 构建，用于查询、搜索、报表和缓存 | 可以重建；不得反向覆盖权威对象 |

模块可以共享基础设施，但不得共享数据所有权。组合部署时仍按逻辑模块命名空间、访问权限和合同隔离；任何模块不得直接修改另一个模块的数据，也不得把跨模块引用设计成共同拥有。

## 4. 对象创建顺序

实施和迁移应按以下依赖顺序：

1. Account；
2. User 与 Account 成员关系；
3. Team、Role、Capacity；
4. Inbox 与 Inbox 成员；
5. Company、Label、自定义字段定义；
6. Contact；
7. ContactInbox；
8. Conversation；
9. Message 与 Attachment；
10. Assignment、Participant、Notification、SLA 结果；
11. Automation、Campaign、Portal；
12. Assistant、知识、Integration 和 Webhook；
13. 审计、报表派生信息和兼容映射。

## 5. 关键唯一规则

| 范围 | 目标规则 | 冲突处理 |
|---|---|---|
| Account | id 唯一 | 拒绝重复主键 |
| User | 登录邮箱按目标标准化规则唯一 | 返回现有身份或明确冲突 |
| Contact | identifier 在 Account 内唯一；邮箱和电话按接口规则匹配 | 先查重，不能静默覆盖 |
| ContactInbox | inbox_id + source_id 唯一 | 复用现有渠道身份或冲突 |
| Conversation | display_id 在 Account 内唯一 | 旧 ID 映射到稳定目标 ID |
| Message | Provider 外部消息 ID 在渠道范围内唯一 | 重复入站只更新状态或忽略 |
| Webhook 事件 | 订阅范围 + event_id 唯一 | 重复投递不重复执行业务动作 |
| 计费事件 | Provider event_id 唯一 | 重复回调不重复计费 |

## 6. 生命周期核对

每个对象必须回答：

- 谁可以创建、更新、停用和删除；
- 删除是硬删除、软删除、脱敏、解绑还是延迟清理；
- 子对象如何处理；
- 历史消息、报表、审计和外部关联是否保留；
- 列表、详情、搜索、实时事件和导出是否还能看到；
- 重复执行删除是否幂等；
- 删除期间并发写入如何处理；
- 恢复或回退是否允许。

## 7. 模块拆分迁移流程

1. 冻结 foundation_version、模块合同版本、对象清单、所有权和源目标运行单元；
2. 记录迁移起点的对象总量、最大 object_version、最大 source_sequence 和 Change 水位；
3. 将历史权威对象和 Local Change Journal 复制到目标模块边界，保持原标识、版本和时间；
4. 启动影子实例，以只读方式回放起点后的 Change，并比较查询、事件和指标结果；
5. 保持源模块为唯一写入权威，禁止源目标双权威写入；
6. 在差异为零且延迟低于基线阈值后，将新命令灰度路由到目标模块；
7. 切换写入权威，记录切换 change_id、时间、水位和路由版本；
8. 对切换后的对象、Change、事件、投影和指标执行持续对账；
9. 发现不可接受差异时停止新写入，回放切换后 Change 到原权威并回退路由；
10. 稳定观察期结束后再停用旧写入入口，历史映射和审计链继续保留。

## 8. 合并部署规则

合并是运行位置变化，不是模块边界消失。合并到 U1 至 U5 或同一运行进程后：

- 外部接口、Action Capability、Process Intent、命令和事件合同保持不变；
- owner_module、module_id、change_id、object_version 和 source_sequence 保持不变；
- 模块间调用仍通过公开合同，不允许因为同进程而直接读取或修改对方权威数据；
- Local Change Journal 仍按逻辑模块独立记录和对账；
- 权限、限流、故障隔离、指标和审计仍能按逻辑模块区分；
- 再次拆分时不需要改变业务对象、外部合同或数据语义。

## 9. Change 对账规则

| 对账面 | 核对内容 | 通过条件 |
|---|---|---|
| 权威对象与 Local Journal | 每次版本变化对应唯一 change_id；前后版本连续 | 缺口、重复、倒退均为 0 |
| Local Journal 与集中 AUD | change_id、module_id、account_id、对象和版本一致 | 已过允许延迟后差异为 0 |
| Change 与领域事件 | 应发布的事件存在且 causation 指向对应 Change 或命令 | 遗漏、错链和无法解释的重复均为 0 |
| 事件与投影 | 搜索、报表、列表和缓存达到同一对象版本 | 超过时效阈值的落后为 0 |
| 批量迁移前后 | 总量、唯一键、关系、状态、哈希和版本水位一致 | 预先声明的过滤项外差异为 0 |
| 拆分或合并前后 | 相同命令得到相同对象结果、Change、事件和业务指标 | 业务语义差异为 0 |

任何自动修复都必须产生新的可追踪 Change，不能改写旧 Journal 或集中审计记录。对账差异必须记录发现时间、范围、原因、修复动作、修复 change_id 和复验结论。

## 10. 完成条件

- [ ] DATA-01 至 DATA-18 全部关闭；
- [ ] 核心对象关系符合 43、44 分册；
- [ ] 创建默认、更新语义、唯一规则和生命周期符合 34 分册；
- [ ] 旧对象到目标对象不存在一对多歧义；
- [ ] 迁移和对账可以使用稳定标识；
- [ ] 任一对象变化都可推导其列表、事件、报表和审计影响。
- [ ] 26 个逻辑模块的数据所有权、外部引用、Local Journal 和可重建投影均有清单；
- [ ] 模块拆分、合并和回退均保持单一写入权威；
- [ ] 组合部署没有绕过模块合同或直接跨模块修改数据；
- [ ] 权威对象、Change、AUD、事件和投影的对账差异为零。
