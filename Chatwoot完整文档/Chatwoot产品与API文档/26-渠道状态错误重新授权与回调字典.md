# Chatwoot 渠道状态、错误、重新授权与回调字典

> 导航：[渠道授权、通话、会议与高级 Inbox API](15-渠道授权通话会议与高级Inbox-API.md)｜[各渠道创建更新字段字典](17-各渠道创建更新字段字典.md)

## 1. 状态设计

渠道可用性不是单一 boolean，而是以下状态共同决定：

| 层次 | 关注内容 |
|---|---|
| Account Feature | 渠道入口是否允许使用 |
| 安装凭证 | App ID、Secret、API 版本和验证 Token 是否齐全 |
| Inbox 配置 | 号码、邮箱、Page、业务账号和 Provider 参数是否完整 |
| 授权状态 | Access Token 是否有效、权限范围是否足够 |
| Webhook 状态 | 第三方事件是否投递到当前实例 |
| 发送状态 | Provider 是否接受、投递、已读或失败 |
| 重新授权状态 | 连续认证错误是否达到需要人工处理的阈值 |

因此 Inbox 列表可见不代表渠道健康，发送成功也不代表 Webhook 入站正常。

## 2. Inbox 渠道状态字段

| 字段 | 类型 | 说明 |
|---|---|---|
| id | integer | Inbox ID |
| name | string | Inbox 名称 |
| channel_type | string | 渠道类型 |
| channel_id | integer | 渠道配置对象 ID |
| reauthorization_required | boolean | 是否需要重新授权 |
| enable_auto_assignment | boolean | 是否启用自动分配 |
| working_hours_enabled | boolean | 是否启用工作时间 |
| out_of_office_message | string | 非工作时间自动回复 |
| greeting_enabled | boolean | 是否启用欢迎语 |
| greeting_message | string | 欢迎语内容 |
| csat_survey_enabled | boolean | 是否启用 CSAT |
| message_templates | array | 可用消息模板，适用于模板渠道 |

reauthorization_required 只在支持重新授权判断的渠道中有业务意义。当前重点包括 Facebook、Instagram、TikTok、Google Email、Microsoft Email，以及通过 Embedded Signup 建立的 WhatsApp Cloud Inbox。

## 3. 重新授权触发规则

| 渠道 | 触发特点 | 处理动作 |
|---|---|---|
| Facebook | 连续认证错误达到阈值后标记 | 通知 Account Administrator，重新完成 Page 授权 |
| Instagram | 一次明确认证错误即可标记 | 重新完成 Instagram 业务账号授权 |
| TikTok | 一次明确认证错误即可标记 | 重新完成 TikTok 授权 |
| Google Email | Provider 配置缺失或授权错误标记 | 重新授权邮箱并确认 Refresh Token |
| Microsoft Email | Provider 配置缺失或授权错误标记 | 重新授权邮箱并确认租户和权限 |
| WhatsApp Embedded | 授权错误且 Inbox 来自 Embedded Signup 时标记 | 使用 WhatsApp 重新配置流程 |

Facebook 等默认在连续 2 次认证错误后要求重新授权；Instagram 和 TikTok 在首次明确认证错误后即可标记。成功更新有效渠道凭证后应清除标记。

手工填写 API Key 建立的 WhatsApp Inbox 不使用相同的 reauthorization_required 展示逻辑，应通过 health、消息错误和 Provider 控制台判断凭证状态。

## 4. 重新授权通知

达到重新授权条件后，系统向 Account Administrator 产生通知。通知应至少能定位：

| 信息 | 用途 |
|---|---|
| account_id | 确认受影响租户 |
| inbox_id | 定位渠道 |
| channel_type | 选择正确授权流程 |
| channel_name | 供页面展示 |
| error_summary | 区分 Token、权限、资源不存在或 Provider 拒绝 |
| created_at | 判断故障开始时间 |

通知只提示需要处理，不包含第三方 Secret 或完整 Token。

## 5. 通用授权结果

授权型渠道通常先取得授权 URL，再由第三方回调。

| 结果字段 | 类型 | 说明 |
|---|---|---|
| success | boolean | 授权是否完成 |
| url 或 redirect_url | string | 需要跳转的第三方授权地址 |
| id | integer | 成功创建或更新的 Inbox ID |
| name | string | Inbox 名称 |
| channel_type | string | 新建渠道类型 |
| message | string | 成功或失败摘要 |
| error | string | 错误 Key 或简短错误 |
| error_message | string | 可向管理员展示的错误说明 |

OAuth state 用于绑定 Account、请求发起人、回调目标和过期时间。state 过期、被篡改或与当前会话不匹配时必须拒绝回调。

## 6. 授权错误分类

| 类别 | 常见表现 | 处理建议 |
|---|---|---|
| access_denied | 用户在第三方页面取消 | 返回授权入口，不创建 Inbox |
| invalid_state | state 缺失、过期或不匹配 | 重新发起完整授权，不能复用旧回调 URL |
| invalid_code | code 已使用、过期或错误 | 重新授权 |
| missing_scope | 缺少读取消息、发送消息或管理 Webhook 权限 | 在第三方应用补充权限后重新授权 |
| invalid_token | Access Token 或 Refresh Token 失效 | 重新授权并替换旧 Token |
| resource_not_found | Page、号码、店铺、团队或 Workspace 不存在 | 确认资源仍属于授权账号 |
| configuration_missing | 安装 App ID、Secret 或回调地址未配置 | 先完成 24 分册中的安装配置 |
| provider_error | 第三方服务异常或限流 | 保留错误摘要并按 Retry-After 或稍后重试 |

## 7. Facebook 授权与回调

### 7.1 授权入口

| 方法 | 路径 | 主要输入 |
|---|---|---|
| GET、POST | /api/v1/accounts/{account_id}/callbacks/register_facebook_page | 发起或完成 Page 登记 |
| POST | /api/v1/accounts/{account_id}/callbacks/facebook_pages | 查询当前授权用户可管理的 Page |
| POST | /api/v1/accounts/{account_id}/callbacks/reauthorize_page | 重新授权已有 Page Inbox |
| GET、POST | /bot | Facebook Messenger 验证和 Page 事件入口 |

成功授权后需要选择可管理的 Page，并为每个目标 Page 建立或更新 Inbox。Page ID 在 Account 范围内应保持唯一，不能把同一 Page 静默绑定到多个冲突 Inbox。

### 7.2 失败处理

- 用户拒绝授权时不创建 Inbox；
- Page Token 无效时累计认证错误；
- 权限不足时不能仅依赖重新请求消息来恢复；
- Page 被移除或应用订阅丢失时，需要重新授权并检查 Webhook；
- Human Agent 能力还取决于第三方应用审批。

## 8. Instagram 授权与回调

| 方法 | 路径 | 功能 |
|---|---|---|
| POST | /api/v1/accounts/{account_id}/instagram/authorization | 获取 Instagram 授权入口 |
| GET | /instagram/callback | 处理授权结果 |
| GET、POST | /webhooks/instagram | 验证和接收 Instagram 事件 |

回调错误可以包含 error_type、error_code 和 error_message。页面应优先展示可理解的 error_message，同时保留错误类型用于分类。Instagram 认证错误阈值为 1，出现明确认证失败后应尽快要求重新授权。

## 9. TikTok 授权与回调

| 方法 | 路径 | 功能 |
|---|---|---|
| POST | /api/v1/accounts/{account_id}/tiktok/authorization | 获取 TikTok 授权入口 |
| GET | /tiktok/callback | 处理授权结果 |
| POST | /webhooks/tiktok | 接收 TikTok 事件 |

TikTok 回调错误同样可映射为 error_type、error_code、error_message。认证错误阈值为 1。重新授权前应确认应用版本、回调 URL 和应用权限未发生变化。

## 10. Google Email 授权

| 方法 | 路径 | 功能 |
|---|---|---|
| POST | /api/v1/accounts/{account_id}/google/authorization | 生成 Google 授权 URL |
| GET | /google/callback | 交换授权结果并创建或更新 Email Inbox |

授权上下文应包含 account_id、当前 User 和可选 return_to。成功后保存邮箱身份和 Provider 配置；Provider 配置为空或 Refresh Token 失效时，Inbox 可标记 reauthorization_required。

常见失败包括 redirect URI 不一致、Refresh Token 未返回、用户取消、Scope 不足和邮箱已绑定。

## 11. Microsoft Email 授权

| 方法 | 路径 | 功能 |
|---|---|---|
| POST | /api/v1/accounts/{account_id}/microsoft/authorization | 生成 Microsoft 授权 URL |
| GET | /microsoft/callback | 交换授权并创建或更新 Email Inbox |
| GET | /.well-known/microsoft-identity-association.json | Microsoft 应用域名身份关联 |

回调需要校验 state、授权租户、邮箱身份和权限范围。Provider 配置缺失或 Refresh Token 失效时应重新授权，而不是继续使用普通 SMTP 字段覆盖授权邮箱配置。

## 12. X/Twitter 授权与事件

| 方法 | 路径 | 功能 |
|---|---|---|
| POST | /api/v1/accounts/{account_id}/twitter/authorization | 启动授权流程 |
| GET | /twitter/callback | 处理授权结果 |
| GET、POST | /webhooks/twitter | Webhook 验证与事件接收 |

授权过程中的临时 Token 与最终访问 Token 不能混用。Webhook 验证和消息事件应共用正确的应用环境与 Account Activity 配置。

## 13. WhatsApp Embedded Signup 与重新配置

### 13.1 授权接口

| 方法 | 路径 | 功能 |
|---|---|---|
| POST | /api/v1/accounts/{account_id}/whatsapp/authorization | 用 Embedded Signup 结果创建或更新 Inbox |
| GET、POST | /webhooks/whatsapp | 验证和接收 WhatsApp Cloud 事件 |

### 13.2 请求字段

| 字段 | 必填 | 说明 |
|---|---:|---|
| code | 是 | Embedded Signup 一次性授权 code |
| business_id | 是 | Meta Business ID |
| waba_id | 是 | WhatsApp Business Account ID |
| phone_number_id | 否 | 已选择的电话号码 ID；流程可在交换结果后确定 |
| inbox_id | 重新配置时是 | 需要更新的现有 Inbox |

### 13.3 成功响应

| 字段 | 说明 |
|---|---|
| success | true |
| id | 创建或更新的 Inbox ID |
| name | Inbox 名称 |
| channel_type | Channel::Whatsapp |
| message | 完成摘要 |

重新配置必须保持原 Inbox 的 Account 归属，不能通过 inbox_id 修改其他 Account 的号码。

## 14. WhatsApp Health API

| 方法 | 路径 | 权限 | 适用范围 |
|---|---|---|---|
| GET | /api/v1/accounts/{account_id}/inboxes/{inbox_id}/health | Administrator | WhatsApp Cloud Inbox |

| 响应字段 | 说明 |
|---|---|
| id | 号码 ID |
| display_phone_number | 展示电话号码 |
| verified_name | 已验证企业名 |
| name_status | 名称审核状态 |
| quality_rating | 质量评级 |
| messaging_limit_tier | 消息发送层级 |
| account_mode | 账号模式 |
| code_verification_status | 号码验证状态 |
| webhook_configuration | 当前 Webhook 配置 |
| expected_webhook_url | Chatwoot 期望的 Webhook URL |
| throughput | 当前吞吐能力 |
| last_onboarded_time | 最近接入时间 |
| platform_type | 平台类型 |
| certificate | 证书信息，存在时返回 |
| business_id | Business ID |

health 不适用于 Twilio WhatsApp 或缺少 API Key、phone_number_id 的 Inbox。错误时应区分“不支持此渠道”和“Cloud 配置缺失”。

## 15. WhatsApp Webhook 重新登记

| 方法 | 路径 | 功能 |
|---|---|---|
| POST | /api/v1/accounts/{account_id}/inboxes/{inbox_id}/register_webhook | 为 WhatsApp Cloud 重新登记回调 |

登记成功只表示 Provider 接受配置。随后还应使用实际入站消息验证签名、事件接收、ContactInbox 映射和消息去重。

## 16. 消息模板同步

| 方法 | 路径 | 适用渠道 |
|---|---|---|
| POST | /api/v1/accounts/{account_id}/inboxes/{inbox_id}/sync_templates | WhatsApp Cloud、Twilio WhatsApp |

同步是异步或 Provider 依赖流程。请求成功后应再次读取 Inbox 模板列表，检查 template_id、name、language、category、status 和 components。

常见模板状态包括 PENDING、APPROVED、REJECTED、PAUSED 和 DISABLED。只有 Provider 允许发送的状态才能用于业务消息。

## 17. CSAT 模板状态

### 17.1 接口

| 方法 | 路径 | 功能 |
|---|---|---|
| GET | /api/v1/accounts/{account_id}/inboxes/{inbox_id}/csat_template | 查询模板是否存在和审核状态 |
| POST | /api/v1/accounts/{account_id}/inboxes/{inbox_id}/csat_template | 创建模板 |
| POST | /api/v1/accounts/{account_id}/inboxes/{inbox_id}/csat_template/analyze | 分析模板状态和可用性 |

### 17.2 查询字段

| 渠道 | 主要字段 |
|---|---|
| WhatsApp Cloud | template_exists、template_name、status、template_id |
| Twilio WhatsApp | template_exists、friendly_name、content_sid、status、language |

创建 WhatsApp 模板后通常先返回 PENDING；Twilio 模板通常先返回 pending。审核完成前不能假设模板可发送。

### 17.3 错误

| HTTP 状态 | 场景 |
|---|---|
| 400 | Inbox 渠道不支持 CSAT 模板 |
| 422 | 缺少消息内容、语言或必要渠道参数 |
| 500 | Provider 服务异常 |

Provider 错误详情可包含 code、subcode、type、title 和 message，但不能回传 Secret 或完整 Access Token。

## 18. 消息发送状态

| status | 含义 | 后续动作 |
|---|---|---|
| sent | Chatwoot 或 Provider 已接受发送 | 等待 delivery 回调 |
| delivered | Provider 确认到达接收端 | 可用于送达统计 |
| read | Provider 确认客户已读 | 只有支持已读回执的渠道才出现 |
| failed | 发送失败 | 查看 external_error，必要时修复后 retry |

| 相关字段 | 说明 |
|---|---|
| source_id | Provider 消息 ID，用于状态回调匹配 |
| content_attributes.external_error | 可向管理员展示的第三方错误摘要 |
| content_attributes.is_unsupported | 入站内容是否无法完整呈现 |
| created_at | Chatwoot 接收或创建时间 |
| updated_at | 最近状态更新时间 |

## 19. 失败消息重试

| 方法 | 路径 | 使用条件 |
|---|---|---|
| POST | /api/v1/accounts/{account_id}/conversations/{conversation_id}/messages/{message_id}/retry | 消息属于当前 Account、状态为 failed、渠道仍可发送 |

重试前需要判断：授权是否恢复、模板是否已批准、回复窗口是否仍有效、附件是否可访问、号码是否活跃。不能对 sent、delivered 或 read 消息重复重试。

## 20. 通话状态

| status | 含义 | 是否终态 |
|---|---|---:|
| ringing | 正在呼叫 | 否 |
| in_progress | 已接通 | 否 |
| completed | 正常结束 | 是 |
| no_answer | 无人接听 | 是 |
| failed | 呼叫失败 | 是 |
| rejected | 被拒绝 | 是 |

状态回调可能晚于用户页面操作，终态不应被较早的 ringing 或 in_progress 回调覆盖。

| /webhooks/sms/{phone_number} | POST | 通用短信事件；路径值定位号码 |

## 22. 回调处理规则

- 先验证签名、验证 Token 或 challenge，再读取业务字段；
- 使用 Provider 事件 ID 或消息 ID 去重；
- 快速返回 2xx，耗时处理与回调响应分离；
- 同一事件可能重复、乱序或延迟到达；
- 无法定位 Inbox 时记录安全摘要，不创建无归属 Contact 或 Conversation；
- 只在 Provider 明确要求时响应 challenge；
- 回调错误内容不能包含 Secret、完整 Token、客户附件原文或不必要的个人数据。

## 23. 重新授权完整流程

1. 识别 reauthorization_required 或连续认证错误；
2. 确认受影响的 Account、Inbox、渠道资源和最近成功时间；
3. 检查安装 App ID、Secret、API 版本和回调 URL；
4. 从当前 Inbox 的重新授权入口发起流程；
5. 校验 state，并使用新的 code 交换凭证；
6. 更新同一 Inbox，不创建重复渠道；
7. 清除重新授权标记；
8. 重新登记或验证 Webhook；
9. 分别验证入站消息、出站消息和状态回调；
10. 检查失败消息是否适合人工重试。

## 24. 验收矩阵

| 场景 | 预期结果 |
|---|---|
| 用户取消 OAuth | 不创建 Inbox，返回可理解的取消信息 |
| state 过期 | 拒绝回调并要求重新发起授权 |
| Instagram Token 失效 | 首次明确认证错误后标记重新授权 |
| Facebook 短暂单次错误 | 不立即标记；达到阈值后标记 |
| WhatsApp Cloud 健康检查 | 返回号码、质量、限制和 Webhook 对比信息 |
| 不支持的 Inbox 调 health | 返回明确的不支持或配置缺失错误 |
| 模板处于 PENDING | 不能作为已批准模板发送 |
| failed 消息修复后 retry | 产生新的发送尝试并更新状态 |
| 重复状态回调 | 不重复创建消息，不让状态倒退 |
| Webhook 签名错误 | 拒绝处理且不暴露校验凭证 |

各 Provider 的互斥时间、自动重试序列、回调确认、消息回声、状态乱序和限流规则见 [异常、超时、重试、限流与第三方差异规则](36-异常超时重试限流与第三方差异规则.md)。
