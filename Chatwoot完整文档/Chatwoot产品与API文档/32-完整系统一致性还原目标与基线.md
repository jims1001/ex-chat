# Chatwoot 完整系统一致性还原目标与基线

> 导航：[全体功能与 API 总表](00-全体功能与API总表.md)｜[完整系统一致性对照验收规范](37-完整系统一致性对照验收规范.md)

## 1. 目标

本分册定义“100% 一致性还原”在可验收范围内的含义。一致性不只是页面有相同按钮、API 有相同路径，还要求在相同前置状态、相同输入、相同时间和相同第三方结果下，产生相同的可观察结果。

可观察结果包括：

- HTTP 状态、Header 和响应字段；
- Account、Inbox、Contact、Conversation、Message 等业务对象的最终状态；
- 实时事件、Webhook、Notification、Activity 和邮件；
- 向第三方 Provider 发起的请求及其次数；
- 文件、附件、导入结果和报表结果；
- 状态变化顺序、可接受的延迟范围和终态；
- 失败时的错误、补偿、重试和副作用。

## 2. 一致性等级

| 等级 | 目标 | 判定标准 |
|---|---|---|
| L1 功能一致 | 功能模块和业务动作存在 | 00、01、23 和 30 分册中的功能可找到对应入口 |
| L2 合约一致 | 请求、响应、字段、权限和错误一致 | 相同请求获得相同状态和字段语义 |
| L3 行为一致 | 业务状态、事件、通知和外部请求一致 | 正常、异常和重复请求结果一致 |
| L4 时序一致 | 并发、乱序、超时和重试一致 | 在允许的时间窗口内进入相同终态 |
| L5 运行一致 | 限流、容量、第三方故障和历史数据行为一致 | 压力、故障、升级数据和回退场景结果一致 |

“验收层面 100%”指纳入基线的 L1 至 L5 场景全部通过。它不表示对无限的未知输入做出绝对承诺。

## 3. 一致性公式

每个场景必须固定以下五类条件：

| 条件 | 内容 |
|---|---|
| 版本基线 | Chatwoot 4.16.0、Edition、功能套餐和依赖的第三方 API 版本 |
| 配置基线 | 安装配置、Account Feature、Account Limit、Inbox 设置和 Provider 能力 |
| 数据基线 | 测试开始前所有业务对象、状态、时间和关联关系 |
| 输入基线 | 请求、事件、文件、第三方响应、时钟和并发顺序 |
| 观察窗口 | 同步响应截止时间、异步等待时间和最终超时点 |

只有这些条件相同，结果才能用于一致性判定。

## 4. 版本基线

| 项目 | 必填内容 |
|---|---|
| 产品版本 | 4.16.0 |
| Edition | 社区版或企业版 |
| Cloud 状态 | Cloud 或自管理实例 |
| 时区 | 实例时区、Account reporting_timezone、Inbox timezone |
| 语言 | 实例默认语言、Account locale、Portal locale |
| 第三方 API 版本 | Facebook、Instagram、WhatsApp、TikTok、Notion 等实际配置值 |
| 移动端配置 | 深度链接、Android Package、iOS App ID、Push Provider |
| AI 基线 | Provider、Endpoint、Model、Feature 映射和额度 |

版本基线改变后，原验收结果不自动适用，必须重新执行受影响的场景。

## 5. 安装配置基线

102 个安装配置的完整清单见 24 分册。一致性验收至少要锁定以下类别：

| 类别 | 影响 |
|---|---|
| 公开地址和品牌 | OAuth 回调、邮件链接、帮助中心和移动端跳转 |
| 注册和登录 | 是否允许注册、Google OAuth、SAML、MFA、会话数量 |
| 邮件 | 发件人、入站域、Account 每日限额和 Transcript |
| 渠道密钥 | 授权、签名校验、消息发送和回调 |
| Webhook | 超时、签名、安装级事件和错误后动作 |
| 安全和限流 | 登录、Widget、上传、删除、搜索和报表阈值 |
| Captain | Provider、Model、知识抓取、同步和转录 |

Secret 在基线中只记录“已配置、未配置、版本号或指纹”，不记录完整值。

## 6. Account 基线

| 类别 | 必须固定的值 |
|---|---|
| Account | id、status、locale、reporting_timezone、settings |
| Feature | 68 个 Feature 的启用结果 |
| Limit | agents、conversations、non_web_inboxes、captain、emails 等 |
| 成员 | User、role、custom_role_id、availability、auto_offline |
| 团队 | Team、Team Member |
| 容量 | Agent Capacity Policy、Inbox Limit |
| 分配 | Assignment Policy、Inbox 绑定、顺序和优先级 |
| 时间 | Account 时区、Inbox 工作时间、节假日和当前时钟 |

Feature 打开不等于必然可用。企业授权、Account status、Limit、角色、Inbox 类型和 Provider 配置必须同时记录。

## 7. Inbox 和 Provider 基线

| 项目 | 必须记录 |
|---|---|
| Inbox | id、name、channel_type、timezone、working_hours_enabled |
| 消息规则 | allow_messages_after_resolved、lock_to_single_conversation、greeting、email_collect |
| 分配 | enable_auto_assignment、assignment_policy、members、capacity |
| 渠道身份 | phone_number、page_id、business_id、bot_token 指纹、line_channel_id |
| Provider | 平台类型、API 版本、回调地址、能力开关 |
| 模板 | 名称、语言、审核状态、组件 |
| 语音 | inbound_calls_enabled、会议和录音能力 |
| 健康 | 授权状态、Webhook 登记状态、最近错误 |

真实凭证可以用行为可控的 Provider 测试账号替代，但两个对照系统必须使用能力相同的账号。

## 8. 数据基线包

每次验收都应从可重置的数据基线开始。

| 数据集 | 必备场景 |
|---|---|
| User | Administrator、Agent、Custom Role、Super Admin、未确认、MFA |
| Account | active、suspended、不同 Feature 和 Limit |
| Inbox | Website、Email、API、WhatsApp、Twilio、LINE、Telegram、社交渠道 |
| Contact | visitor、lead、customer、blocked、重复 email、重复 phone_number |
| Conversation | open、resolved、pending、snoozed、已分配、未分配 |
| Message | sent、delivered、read、failed、incoming、outgoing、activity、template |
| Automation | 常用 Condition、Macro、Campaign、Webhook |
| Report | 跨日、跨时区、重开会话、SLA 达标和违约 |
| Captain | Assistant、Document、FAQ、Copilot Thread、Custom Tool |
| 异步任务 | pending、processing、completed、failed、abandoned |

基线包必须记录对象 ID 间的对应关系，但对比时不要求两个系统产生相同的自动 ID。应通过业务标识和映射表对齐。

## 9. 时钟和时区基线

| 场景 | 固定项 |
|---|---|
| Campaign | scheduled_at 和触发时刻 |
| SLA | 会话创建、第一次回复、下一次回复和解决时间 |
| 工作时间 | Inbox timezone、工作日和休息时段 |
| Report | reporting_timezone、since、until、interval |
| Snooze | snoozed_until |
| Token | 生成时间、过期时间和使用时间 |
| 限流 | 窗口起点、IP、User、Account 和 Token |

不固定时钟时，只能对比相对持续时间，不能对比绝对时间戳。

## 10. 第三方事件包

每个 Provider 至少准备：

- 正常文本、附件、Location、Contact、Reply 和 Echo；
- sent、delivered、read、failed 状态；
- 相同 Event ID 重复三次；
- 乱序状态，例如 read 早于 delivered；
- 错误签名、过期签名、无效 Token 和未知事件；
- 429、5xx、连接超时、读取超时和无效 JSON；
- Provider 已接收但请求方未收到成功响应；
- 回调先于本地发送结果保存完成。

29 分册定义入站字段，19 分册定义出站事件。测试包中的原始请求体必须和签名对应，不能在生成签名后再格式化。

## 11. 观察记录

每个场景应生成一份观察记录：

| 字段 | 说明 |
|---|---|
| scenario_id | 稳定场景编号 |
| baseline_id | 版本、配置和数据基线编号 |
| started_at | 场景开始时间 |
| inputs | 已脱敏的请求、事件和第三方结果 |
| synchronous_result | HTTP 和即时结果 |
| state_changes | 新建、更新、删除或保持不变的对象 |
| emitted_events | 实时事件、Webhook、Notification 和 Activity |
| external_requests | Provider、方法、目标、次数和结果 |
| asynchronous_result | 任务终态和达到终态的时间 |
| differences | 对照差异和是否属于允许差异 |

## 12. 可归一化差异

下列值可以先归一化再对比：

| 类型 | 归一化方式 |
|---|---|
| 自动 ID | 通过场景内业务标识映射 |
| created_at、updated_at | 在允许偏差内比较或转为相对时间 |
| 随机 Token | 只比较存在性、格式、有效期和一次性 |
| 签名 | 使用各自基线 Secret 重算并验证 |
| 临时 URL | 比较目标资源、权限和过期语义 |
| 数组顺序 | 只在文档明确为无序集合时排序比较 |
| Provider ID | 使用请求与响应录制中的映射 |

不得归一化状态、金额、角色、权限、消息内容、失败码、事件次数和对外副作用。

## 13. 允许差异登记

如果两个系统存在已知且可接受的差异，必须显式登记：

| 字段 | 说明 |
|---|---|
| difference_id | 差异编号 |
| affected_scenarios | 受影响场景 |
| reason | 第三方随机性、时间偏差、版本差异或已批准变更 |
| normalization | 是否可归一化 |
| tolerance | 可接受范围 |
| expiry | 差异允许的截止日期 |
| owner | 业务责任人 |

未登记差异默认为验收失败。

## 14. 一致性通过条件

一个场景只有同时满足以下条件才能通过：

- 同步响应符合预期；
- 目标对象状态符合预期；
- 不应变化的对象保持不变；
- 事件、通知和外部请求的次数正确；
- 异步结果在观察窗口内进入正确终态；
- 重复、乱序和并发输入没有产生额外副作用；
- 敏感值没有出现在普通响应、错误和观察记录中；
- 所有差异均属于有效的允许差异。

## 15. 变更后重验范围

| 变更 | 必须重验的范围 |
|---|---|
| 产品版本 | 全量 L1 至 L5 |
| Account Feature | 功能入口、权限、限额、页面和 API |
| Provider API 版本 | 授权、发送、入站回调、状态和错误 |
| 时区或工作时间 | Campaign、SLA、Automation、Report、Snooze |
| 角色或 Custom Role | 全部受保护功能和对象范围 |
| 分配策略 | 未分配会话、容量、在线状态和并发领取 |
| AI Provider 或 Model | Task、Copilot、Assistant、FAQ、Document、Tool |
| 限流配置 | 登录、Widget、搜索、报表、上传和删除 |

## 17. 基线验收

- 版本、Edition、Cloud 状态和第三方 API 版本已固定；
- 102 个安装配置和 68 个 Account Feature 已生成快照；
- Account、User、Inbox、Provider、Limit、时区和工作时间已固定；
- 可重置的数据基线包已准备；
- 第三方事件包包含正常、失败、重复、乱序和超时样本；
- 观察窗口、归一化规则和允许差异已审批；
- 每个场景能同时对比 HTTP、业务状态、事件、外部请求和终态。
