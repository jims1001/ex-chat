# Chatwoot 并发、原子性、幂等与状态竞争规则

> 导航：[异步任务、进度、终态与补偿规则](31-异步任务进度终态与补偿规则.md)｜[异常、超时、重试、限流与第三方差异规则](36-异常超时重试限流与第三方差异规则.md)

## 1. 范围

本分册定义同一对象被多个请求、后台任务或第三方回调同时处理时的可观察行为。重点是“最后保留什么、什么不能重复、失败后哪些结果会留下”。

## 2. 通用并发原则

| 场景 | 通用结果 |
|---|---|
| 两个普通更新同时修改同一字段 | 后成功保存的值成为最终值 |
| 两个更新修改不同字段 | 是否合并取决于该接口是局部更新还是整体替换 |
| 请求包含旧的 updated_at | 普通更新不把它当作并发前置条件 |
| 目标在请求期间被删除 | 返回 404 或对象已不可用，不应自动重建 |
| 重复创建违反业务唯一性 | 已有对象保留，新请求返回校验错误或返回已有关系 |
| 后台任务重复取到同一目标 | 应由对象状态、锁定窗口或业务唯一键保证只有一次有效副作用 |

普通 API 没有通用的 If-Match 或版本号冲突响应。需要避免覆盖时，请求方必须先读取最新对象，只提交目标字段，并在验收中加入同时更新场景。

## 3. 可观察的原子操作组

| 操作 | 同一原子组内的结果 |
|---|---|
| 创建 Conversation 并携带首条 Message | Conversation 和首条 Message 一起成功或一起失败 |
| 创建 Contact 并绑定 Inbox | Contact 和 ContactInbox 关系一起保存；远程头像随后处理 |
| 合并 Contact | Conversation、Message Sender、ContactInbox、Note 转移和被合并 Contact 删除作为一个整体 |
| 替换 Team Member | 新增和移除属于同一次成员集合更新 |
| 替换 Inbox Member | 新增和移除属于同一次成员集合更新 |
| 替换 Conversation Participant | 新增和移除属于同一次参与者集合更新 |
| 删除 Message 内容 | 正文替换为已删除标识，同时删除该 Message 的附件 |
| 启用 MFA | 启用状态和首次备用码生成作为一个整体 |
| 一次性 Campaign 进入发送 | 只有一个触发者能把 active 改为 processing |

原子组之外的事情通常是后续副作用。例如文件下载、头像获取、第三方发送、邮件、Webhook 和搜索更新，不应因为它们失败就假设主对象必然回滚。

## 4. Conversation 创建与领取

### 4.1 创建

| 并发输入 | 预期行为 |
|---|---|
| 同一 ContactInbox 同时收到多条消息 | 应优先追加到已有活动 Conversation |
| lock_to_single_conversation=true | 同一 ContactInbox 保留单一会话线程语义 |
| 首条消息同时到达 | 必须测试是否出现重复 Conversation，不能只比较 Message 数量 |
| source_id 已被其他 Inbox 使用 | 必须使用 inbox_id + source_id 确定 ContactInbox，兼容入口只使用 source_id 时存在歧义风险 |

### 4.2 自动分配

自动分配只领取当时仍然未分配的 Conversation。两个分配流程同时命中同一会话时，只有一个能成功设置 assignee，另一个必须跳过。

| 条件 | 影响 |
|---|---|
| Conversation.status | 只有 open 进入常规自动分配 |
| assignee_id | 必须为空 |
| Agent availability | 必须符合当前在线策略 |
| Inbox Member | Agent 必须是目标 Inbox 成员 |
| Capacity | 不能超过 Agent 或 Inbox 容量 |
| Assignment Policy | 按策略顺序、优先级和分组选择 |
| 同时手工分配 | 手工操作先保存后，自动分配必须跳过已分配对象 |

成功领取后才记录容量和发出 assignee_changed 事件。失败的竞争者不能额外增加容量计数或重复发事件。

## 5. Conversation 状态竞争

| 当前状态 | 动作 | 目标状态 |
|---|---|---|
| open | 无 status 的 toggle_status | resolved |
| resolved | 无 status 的 toggle_status | open |
| pending | 无 status 的 toggle_status | open |
| snoozed | 无 status 的 toggle_status | open |
| 任意可用状态 | 提交 status | 设置为提交值 |
| pending | Agent Bot 提交 open | 执行 Bot Handoff 语义 |

会话进入 open 且操作人是 Agent 时，当前 Agent 会被设为 assignee。因此“切换为 open”不只是 status 变化，验收时必须同时比较 assignee。

并发状态操作不带通用版本前置条件，所以必须验收以下情况：

- Agent A resolve 与 Agent B open 同时提交；
- snoozed_until 到期与手工 resolve 同时发生；
- Bot Handoff 与 Agent 手工分配同时发生；
- 客户新消息重开会话时，Agent 同时操作 status。

判定时以最终 Conversation、assignee、snoozed_until、Activity 和事件顺序为准。

## 6. 已读位置与未读数

| 场景 | 规则 |
|---|---|
| 有未读消息 | update_last_seen 立即更新相关已读时间 |
| 没有未读消息 | 相关已读时间一小时内可能不重复写入 |
| 当前 User 是 assignee | 同时更新 agent_last_seen_at 和 assignee_last_seen_at |
| 当前 User 不是 assignee | 只更新 agent_last_seen_at |
| 标记未读 | 已读位置移到最后一条 incoming Message 之前一秒 |

并发打开会话时，不应以 updated_at 是否变化判定 update_last_seen 失败。在没有未读消息时，一小时节流本身就是预期行为。

## 7. Message 创建和 Echo 幂等

| 标识 | 用途 |
|---|---|
| Message.id | Chatwoot 内部业务标识 |
| echo_id | 请求方的临时消息标识，用于把实时事件与本地临时消息合并 |
| source_id | Provider Message ID，用于状态回调、Reply 和入站去重 |
| X-Chatwoot-Delivery | 单次出站 Webhook 投递标识 |
| Provider Event ID | 第三方事件去重标识 |

echo_id 用于客户端合并显示，不应被当作所有渠道的持久幂等键。发送 Message 超时后，必须先查询会话消息和 source_id，不能立即重复提交。

## 8. Provider 入站串行窗口

| Provider | 串行维度 | 窗口 | 冲突后行为 |
|---|---|---:|---|
| Facebook Messenger | sender_id + recipient_id | 短窗口 | 每 1 秒重试，最多 8 次 |
| Instagram | Contact Instagram ID + Business Account ID | 3 秒 | 第 1、2、3 秒重试；仍冲突时最终不带串行保护继续处理 |
| WhatsApp | Inbox + Contact Sender ID | 30 秒 | 每 2 秒重试，最多 20 次 |
| TikTok | Business ID + Conversation ID | 10 秒 | 每 2 秒重试，最多 8 次 |

这些窗口主要用于降低同一客户首消息同时创建重复 ContactInbox 或 Conversation 的风险，不代表对 Provider 全局事件顺序做出承诺。

Instagram 在三次等待后优先“不丢弃事件”，因此必须额外验收极端并发时的重复 Conversation 风险。

## 9. Message 状态竞争

### 9.1 通用状态更新

Message 状态为 sent、delivered、read、failed。通用状态更新保护明确阻止 read 回退为 delivered，但不能由此推断所有 Provider 的状态都严格单调。

| 当前状态 | 新回调 | 通用结果 |
|---|---|---|
| sent | delivered | delivered |
| sent | read | read |
| sent | failed | failed，保存 external_error |
| delivered | read | read |
| read | delivered | 忽略，保持 read |
| failed | sent | 只有明确 retry 流程应进入 sent |

### 9.2 渠道差异

Twilio Delivery 和通用 SMS Delivery 直接应用已识别状态。因此对照验收不能用“所有渠道绝不回退”作为统一规则，而应使用 36 分册的渠道状态矩阵。

external_error 在通用状态服务中只在 failed 时保留，后续成功状态会清除它。但直接应用 Provider 状态的渠道可能只在有错误时更新 external_error。

## 10. Message 删除与重试竞争

DELETE Message 不是立即移除 Message 记录，而是：

- 把 content 替换为已删除文案；
- 把 content_type 设为 text；
- 把 content_attributes 替换为 deleted=true；
- 删除该 Message 的所有附件。

删除与 Provider 状态回调同时发生时，Message 记录仍可能接收状态更新，但内容不应恢复。

retry 操作会：

1. 把 Message 状态改为 sent；
2. 清空 content_attributes；
3. 重新发起渠道发送。

因此 retry 不应与内容属性编辑、删除或另一次 retry 并发执行。只对 failed Message 开放 retry，并在重试前保存必要的 Provider 错误证据。

## 11. Contact 合并

| 规则 | 结果 |
|---|---|
| base_contact_id = mergee_contact_id | 直接返回 base Contact，不产生副作用 |
| 两个 Contact 必须属于同一 Account | 跨 Account 合并失败 |
| Conversation | 转移到 base Contact |
| Message Sender | 从 mergee Contact 转为 base Contact |
| ContactInbox | 转移到 base Contact |
| Note | 转移到 base Contact |
| 字段冲突 | base Contact 的非空值优先 |
| mergee Contact | 转移完成后删除 |

合并是高风险不可重复动作。两个合并请求同时使用同一 Contact 时，只有第一个能保证基于原始状态完成；后续请求应重新读取 Contact 映射，不能盲目重放。

## 12. 成员与参与者集合

| 资源 | 业务唯一性 | 重复添加 |
|---|---|---|
| AccountUser | account_id + user_id | 不创建第二条成员关系 |
| TeamMember | team_id + user_id | 不创建第二条团队成员关系 |
| InboxMember | inbox_id + user_id | 不创建第二条 Inbox 成员关系 |
| ConversationParticipant | conversation_id + user_id | 重复添加返回已有参与关系 |
| CaptainInbox | assistant_id + inbox_id | 同一 Assistant 不重复绑定 Inbox |

PATCH Team Members、Inbox Members 和 Participants 表示把集合更新为提交的 user_ids。与其他请求并发时，后一次集合替换可能移除前一次刚添加的 User。不能把 PATCH 当作单纯追加。

## 13. Campaign 并发触发

one_off Campaign 只在以下条件同时成立时发送：

- campaign_type=one_off；
- 对应 Feature 可用；
- campaign_status 仍为 active；
- 当前没有其他触发者已把状态改为 processing 或 completed。

多个调度者同时取到同一 Campaign 时，只有第一个能进入 processing。其他触发者不得重复发送。completed Campaign 拒绝继续更新为可重发状态。

## 14. Data Import 并发和重启

| 场景 | 规则 |
|---|---|
| 同一 Account 同时创建多个活动 Intercom Import | 只允许一个进入活动流程，其他创建返回 422 |
| 同一 Import 重复 start | 只有允许的状态进入新运行 |
| failed 或 abandoned 重启 | 保留已导入映射，只补齐未完成部分 |
| 旧运行的延迟任务恢复 | 运行标识与当前活动运行不同时跳过 |
| 同一来源对象重复进入 | data_import_id + source_object_type + source_object_id 用于保持单条处理语义 |
| 跨 Import 重复来源对象 | account_id + source_provider + source_object_type + source_object_id 用于复用已有映射 |

abandon 不能假设正在执行的单条操作在同一时刻立即停止。终态判定应同时检查 Import status、processed_records、Item status 和已创建对象。

## 15. Captain Document 同步

| 规则 | 结果 |
|---|---|
| PDF Document | 不进入网页自动同步 |
| 同一 Document 同时 sync | 一个任务执行，其他任务记录为已在同步 |
| 同步互斥窗口 | 10 分钟 |
| sync_status=syncing 长时间不变 | 超过 2 小时后 sync_in_progress=false，可作为陈旧任务处理 |
| 同一 Assistant 下的 external_link | 必须唯一 |

10 分钟是同时执行保护窗口，2 小时是对外判定陈旧 syncing 的窗口，两者用途不同。

## 16. Call 状态竞争

Call 状态为 ringing、in_progress、completed、no_answer、failed、rejected。

| 情况 | 规则 |
|---|---|
| 同一 Call 同时 accept 和 reject | 只有一个互斥操作先完成，后续操作必须基于新状态判断 |
| 终态后收到早期回调 | 忽略，不覆盖终态 |
| 重复 in_progress | 保留最早 started_at |
| 终态缺少 duration | 使用 ended_at - started_at，最小为 0 |
| 重复录音回调 | 同一 Call 录音只应关联一次 |

Call、Conversation.additional_attributes.call_status 和 Voice Call Message 是同一业务状态的不同表现。验收不能只检查 Call 详情。

## 17. 计费事件和额度

Stripe Event 使用 event.id 作为幂等基准。账号订阅、充值和额度更新必须按 Account 串行，防止两个结算事件同时覆盖额度。

| 场景 | 验收点 |
|---|---|
| 同一 event.id 投递三次 | 余额或订阅只变化一次 |
| 两个不同充值事件并发 | 两笔合法结果都保留，不相互覆盖 |
| 旧订阅事件晚到 | 不能把已更新的有效订阅回退为旧状态 |
| 无效签名 | 返回 400，不改变 Account |

## 18. Webhook 幂等

| 方向 | 幂等标识 | 接收方规则 |
|---|---|---|
| Chatwoot 出站 | X-Chatwoot-Delivery | 相同 Delivery 只处理一次 |
| Message 事件 | event + Message.id | 同一事件不重复发送外部副作用 |
| Conversation 事件 | event + Conversation.id + 关键 updated_at | 按业务需要合并重复更新 |
| Provider 入站 | Provider Event ID 或 Message ID | 相同事件不创建第二个 Message |
| OAuth Callback | code + state | 一次性，失败后重新发起授权 |

如果接收方不保存 X-Chatwoot-Delivery，网络超时后就无法区分“Chatwoot 未发送”与“接收方已处理但成功响应丢失”。

## 19. 重试前的结果查询

| 动作 | 重试前必查 |
|---|---|
| 创建 Contact | identifier、email、phone_number |
| 创建 Conversation | ContactInbox 的活动 Conversation |
| 发送 Message | echo_id、source_id、最近 Message |
| 执行 Macro | Message、Assignment、Label、Activity |
| 触发 Campaign | campaign_status |
| 同步 Document | sync_status、sync_in_progress、last_sync_attempted_at |
| 启动 Import | status、active run、Item 统计 |
| 删除对象 | 详情是否已返回 404 |
| 计费事件 | event.id 是否已完成 |

## 20. 并发验收矩阵

| 编号 | 场景 | 必要断言 |
|---|---|---|
| CC-01 | 两个 Agent 同时领取未分配 Conversation | 只有一个 assignee，只有一次容量增加 |
| CC-02 | 两个调度者同时触发 one_off Campaign | 只发送一次 |
| CC-03 | 同一 Provider Message 同时投递三次 | 只有一条 Message |
| CC-04 | read 早于 delivered | 按渠道状态矩阵得到预期最终状态 |
| CC-05 | Contact Merge 与 Contact Update 并发 | 没有孤立 Conversation、Message 或 ContactInbox |
| CC-06 | Team Member 集合替换并发 | 最终集合完整，不存在重复成员 |
| CC-07 | Document sync 同时提交三次 | 只有一个有效同步流程 |
| CC-08 | Call accept 与 reject 同时提交 | 只有一个最终通话方向 |
| CC-09 | 相同 Stripe Event 重复投递 | 订阅、余额或额度只变化一次 |
| CC-10 | 删除 Message 与 Provider 状态回调并发 | 内容保持删除，附件不恢复 |
| CC-11 | Import 重启后旧运行任务恢复 | 旧任务跳过，不污染新运行 |
| CC-12 | 无未读消息时频繁 update_last_seen | 一小时内允许不重复更新时间 |

## 21. 验收要求

- 每个并发场景至少执行 20 轮，不能只执行一次；
- 每轮改变请求先后顺序和延迟；
- 同时对比 HTTP、最终对象、事件次数、外部请求次数和异步终态；
- 不得把“最终对象数量正确”作为唯一断言，还要检查错误的中间事件和重复外部请求；
- 未定义并发前置条件的普通 PATCH，默认按后成功保存结果验收；
- 所有不可重复动作都必须先执行结果查询。
