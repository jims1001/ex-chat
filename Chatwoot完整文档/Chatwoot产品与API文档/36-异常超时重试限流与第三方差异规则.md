# 异常、超时、重试、限流与第三方差异规则

> 适用版本：Chatwoot 4.16.0
> 本分册固定故障发生时系统可观察到的响应、重试时间、最大次数、最终状态、补偿方式，以及不同第三方渠道之间不能被统一处理的差异。

## 1. 故障行为也是功能的一部分

正常路径一致，不代表系统一致。完整还原还必须回答：

- 何种错误立即失败，何种错误自动重试；
- 超时后请求是否可能已经成功；
- 第几次重试后进入最终失败；
- 重试是否复用原对象和外部标识；
- 用户查询时看到 sent、failed 还是 pending；
- 第三方重复推送是否生成重复消息；
- 回调乱序是否覆盖已确认终态；
- 达到频率限制时按 IP、邮箱、账号、用户还是 Token 计算；
- 自动恢复失败后是否需要重新授权、人工重试或重新创建对象。

本分册应与 [26-渠道状态错误重新授权与回调字典](26-渠道状态错误重新授权与回调字典.md)、[29-第三方入站Webhook完整字段字典](29-第三方入站Webhook完整字段字典.md) 和 [31-异步任务进度终态与补偿规则](31-异步任务进度终态与补偿规则.md) 联合使用。

## 2. 故障分类

| 类别 | 判断特征 | 是否自动重试 | 最终处理 |
|---|---|---|---|
| 认证失败 | Token、签名、密钥、会话无效 | 通常不重试 | 重新登录、轮换密钥或重新授权 |
| 权限失败 | 身份有效但无权访问 | 不重试 | 调整角色、Feature、归属或套餐 |
| 字段校验失败 | 字段缺失、格式、枚举或唯一性错误 | 不重试原请求 | 修正输入后重新提交 |
| 业务状态冲突 | 对象状态不允许当前动作 | 不盲目重试 | 先查询当前状态再决定 |
| 并发互斥 | 同一资源正在被处理 | 按功能延迟重试 | 到达上限后查询最终状态 |
| 频率限制 | 返回 429 或 Provider 限流 | 按规定延迟重试 | 降低速率，尊重 Retry-After |
| 网络连接失败 | 无法连接、连接重置、DNS 等 | 仅幂等或可去重操作可重试 | 保留原业务标识并查询结果 |
| 读取超时 | 未在期限内取得响应 | 结果可能未知 | 先查状态，不能直接重复创建 |
| Provider 5xx | 第三方暂时异常 | 按渠道规则重试 | 超限后记录失败与恢复入口 |
| 永久外部错误 | 无效收件人、模板拒绝、权限撤销 | 不持续重试 | 明确失败原因并修复配置 |
| 内容不可用 | 文件丢失、格式不支持、正文已删除 | 有限重试或直接失败 | 重新上传或终止发送 |
| 系统不可用 | 核心服务或异步处理不可用 | 接受请求与执行结果需分开判断 | 恢复后补偿并对账 |

## 3. 自动重试规则总表

下表中的“最多次数”指当前版本对应任务的总尝试或重试上限语义，验收时必须同时记录实际尝试时间点，避免把“重试次数”和“总尝试次数”混淆。

| 功能 | 触发条件 | 间隔 | 上限 | 超限后的可观察结果 |
|---|---|---:|---:|---|
| Facebook 入站事件互斥 | 同一资源仍在处理 | 1 秒 | 8 次重试 | 停止该轮处理并记录异常 |
| TikTok 入站事件互斥 | 同一资源仍在处理 | 2 秒 | 8 次重试 | 停止该轮处理并记录异常 |
| WhatsApp 入站事件互斥 | 同一资源仍在处理 | 2 秒 | 20 次重试 | 停止该轮处理并记录异常 |
| Instagram 入站事件互斥 | 同一资源仍在处理 | 1、2、3 秒 | 3 次延迟重试 | 最后一次在不继续等待互斥的情况下处理 |
| Slack 消息互斥 | 同一资源仍在处理 | 1 秒 | 8 次重试 | 停止该轮处理并记录异常 |
| Integration Hook 互斥 | 同一 Hook 正被处理 | 3 秒 | 3 次重试 | 本轮失败，等待后续事件或人工恢复 |
| Agent Bot Webhook | 仅外部返回 429 或 500 | 3 秒 | 总计 3 次尝试 | 按 Bot 失败策略更新 Conversation |
| 通用 Data Import 文件处理 | 可重试导入异常 | 1 分钟 | 3 次重试 | Import 进入可诊断失败结果 |
| Intercom Import 普通错误 | Provider 普通可重试错误 | 1 分钟 | 3 次重试 | 当前导入项或运行失败 |
| Intercom Import 频率限制 | Provider 限流 | 1 分钟 | 5 次重试 | 当前导入项或运行失败 |
| Captain Document 同步 | 网络、限流、服务暂不可用 | 30 秒、2 分钟、5 分钟 | 总计 4 次尝试 | Document 进入失败状态 |
| Captain Document 未分类异常 | 其他暂时异常 | 5 秒 | 总计 3 次尝试 | Document 进入失败状态 |
| Captain 网站引导抓取 | 可重试抓取失败 | 递增等待 | 总计 3 次尝试 | 引导抓取失败，可重新发起 |
| Voice Recording 处理 | 录音暂不可取得 | 5 秒 | 3 次重试 | 保留通话，录音标为不可用或失败 |
| Audio 文件暂缺 | 文件尚未准备好 | 2 秒 | 3 次重试 | 音频处理停止并记录原因 |

### 3.1 互斥等待窗口

| 渠道 | 单次互斥有效期 | 设计目的 |
|---|---:|---|
| Facebook | 与短周期重试配合 | 避免同一外部事件并发创建重复对象 |
| Instagram | 3 秒 | 优先保持事件顺序，同时避免长时间阻塞 |
| WhatsApp | 30 秒 | 为同一会话较长处理窗口提供串行化 |
| TikTok | 10 秒 | 避免同一会话或事件交叉处理 |
| Integration Hook | 处理窗口内有效 | 防止同一连接重复执行 |

互斥不是业务完成标志。互斥释放后仍需通过对象状态、外部 ID 和事件记录判断是否已成功。

## 4. 不应自动重试的错误

以下情况重放原请求通常不会自行恢复：

- 密码、Token、签名或 OAuth 授权无效；
- Account 暂停；
- Feature 关闭或套餐无权使用；
- 字段格式、枚举、必填项错误；
- 唯一约束冲突；
- Contact 被阻止；
- Provider 明确返回收件人无效；
- 模板未批准、语言不匹配或模板参数错误；
- 文件类型或大小不受支持；
- Message 已删除；
- Conversation、Inbox、Contact 或 Campaign 已删除；
- Captain Document 来源被永久拒绝访问；
- 第三方明确返回永久资源不存在。

对这些错误应保留可理解的原因，修正前置条件后再发起新操作。

## 5. 超时与“结果未知”

### 5.1 三种超时结果

| 超时阶段 | 可能结果 | 正确恢复方式 |
|---|---|---|
| 请求尚未到达 | 没有任何业务变化 | 使用同一幂等标识重试 |
| 请求已到达但响应丢失 | 操作可能已完成 | 先按业务 ID 或外部 ID 查询 |
| 本地已完成、外部状态未知 | 本地对象存在，Provider 未确认 | 等待回调或执行状态查询 |

### 5.2 超时后禁止直接重复创建的对象

- Conversation；
- Message；
- Contact Inbox；
- Campaign 调度批次；
- Payment 或订阅变更；
- Call；
- Data Import 运行；
- Captain Document 导入；
- Integration Hook；
- Platform Account User 关系。

重试前至少使用一个稳定标识查询：业务对象 ID、source_id、provider_message_id、provider_call_id、delivery_id、run_id 或幂等键。

### 5.3 出站 Webhook 超时

- 默认请求超时为 5 秒，可由安装配置调整；
- 普通 Account Webhook 与 API Inbox Webhook 不应假定存在无限自动重试；
- API Inbox 投递失败时，相关 Message 应进入明确 failed 状态；
- Agent Bot Webhook 只对 429 和 500 按第 3 节规则重试；
- 接收方应使用 delivery ID 去重；
- 接收方响应太慢可能已处理成功，但本系统仍判断为失败，因此接收方必须幂等。

## 6. Agent Bot 失败后的会话状态

Agent Bot Webhook 达到最终失败后：

- 若未启用 keep_pending_on_bot_failure，Conversation 应转为 open，使人工处理可继续；
- 若启用 keep_pending_on_bot_failure，Conversation 保持 pending；
- 失败不应删除客户原始消息；
- 相同 delivery ID 重放不得生成第二个客户消息；
- 429 和 500 以外的错误不进入相同自动重试序列；
- Bot 成功响应后产生的 Message 必须与当前 Conversation 关联；
- Bot 超时与 Bot 明确拒绝需在诊断信息中区分。

## 7. 入站回调的确认策略

第三方回调通常要求尽快确认接收，避免第三方不断重发。确认结果应区分：

| 情况 | 建议确认 | 后续动作 |
|---|---|---|
| 签名或验证 token 错误 | 401、403 或 Provider 规定的拒绝 | 不处理 Payload |
| Challenge 验证成功 | Provider 规定的文本或 200 | 不创建业务事件 |
| 合法且已接受处理 | 200 或 Provider 规定的 204 | 进入正常处理 |
| 合法重复事件 | 200 或 204 | 去重后不再产生副作用 |
| 合法但未知事件类型 | 按 Provider 约定确认 | 记录未知类型，不阻断其他事件 |
| Payload 无法解析 | 400 或 Provider 规定结果 | 记录失败，防止错误数据进入业务对象 |
| 本地暂时异常 | 按渠道约定决定是否让第三方重试 | 必须防止重复副作用 |

具体 Header、签名、Payload 和确认值见 [29-第三方入站Webhook完整字段字典](29-第三方入站Webhook完整字段字典.md)。

## 8. 重复事件去重键

| 事件类型 | 首选去重键 | 辅助范围 |
|---|---|---|
| 入站消息 | provider_message_id | Provider + Channel/Inbox |
| 消息状态 | provider_message_id + status + event time | Provider + Channel |
| WhatsApp 事件 | wamid 或 Provider 事件 ID | Phone Number / Inbox |
| Email | Message-ID 或渠道来源 ID | Email Inbox |
| Call | provider_call_id | Provider |
| Webhook 出站 | delivery_id | Webhook endpoint |
| OAuth 回调 | state + 一次性授权 code | 当前授权会话 |
| Payment 回调 | Provider event ID | Account 或订阅客户 |
| Data Import | run_id + external item ID | 当前 Import |
| Captain Document | Assistant + external_link | 当前 Assistant |

去重记录必须能跨短时网络重试存在，不能只在单次请求期间有效。

## 9. 消息状态的渠道差异

### 9.1 公共状态

Message 可观察的主要状态为：

- sent：已进入发送或本地接受阶段；
- delivered：Provider 确认送达；
- read：Provider 确认已读；
- failed：发送失败；

### 9.2 不能假定所有渠道严格单调

公共消息状态更新会阻止已读状态被较低的 delivered 覆盖，但部分渠道使用各自状态映射，不能把所有 Provider 都视为完全相同。验收必须覆盖：

- delivered 后到 sent；
- read 后到 delivered；
- failed 后到 delivered；
- delivered 后到 failed；
- 相同状态重复到达；
- 未知状态到达；
- 回调不含已知 message ID；
- 状态事件早于消息创建完成到达。

最终结果以对应渠道映射和 [26-渠道状态错误重新授权与回调字典](26-渠道状态错误重新授权与回调字典.md) 为准。

### 9.3 失败原因

Message failed 时应尽量保留：

- Provider 错误码；
- 可公开错误描述；
- 是否可重试；
- 模板、收件人、授权或内容错误分类；
- 最后尝试时间；
- 外部消息 ID；
- 恢复动作。

后续成功状态到达时，公共错误信息应按渠道规则清理或标为历史错误，避免“已送达但仍显示当前失败”。

## 10. 消息回声与出入站识别

部分 Provider 会把本系统发出的消息再次作为回声事件推送。必须核对：

- 回声是否通过外部消息 ID 关联原 Message；
- 不得把回声创建成新的 incoming Message；
- Provider 控制台人工发送的消息是否创建为 outgoing Message；
- 回声中的附件、状态和时间是否补充到原 Message；
- 回声先于发送响应到达时是否仍能合并；
- 相同内容但不同外部 ID 不能只按文本去重；
- 私密备注不得被推送到外部渠道。

## 11. Provider 授权和凭据异常

| 异常 | 可观察结果 | 恢复方式 |
|---|---|---|
| Access Token 过期 | 渠道健康异常、发送失败 | 重新授权或刷新 Token |
| Refresh Token 失效 | 自动刷新失败 | 完整重新授权 |
| 权限范围被撤销 | 部分动作失败 | 重新授权并确认权限集合 |
| Page/Phone/Workspace 被移除 | 资源不可用 | 重新选择有效外部资源 |
| Webhook 订阅失效 | 不再收到入站事件 | 恢复订阅并做缺失事件对账 |
| 签名密钥轮换 | 新回调验证失败 | 在允许窗口支持正确的新旧密钥策略 |
| Provider 版本升级 | 字段、状态或权限变化 | 按版本基线更新映射与验收包 |
| 沙箱与正式环境混用 | 标识存在但请求失败 | 固定环境、凭据和回调域名 |

重新授权后还应验证：新消息、入站回调、状态回调、模板同步、附件和历史会话关联，而不是只验证授权页面成功。

## 12. 不同渠道不可统一的能力

| 能力 | 主要差异 |
|---|---|
| 会话窗口 | WhatsApp 等渠道受外部会话窗口限制，网站聊天通常不相同 |
| 消息模板 | 模板审批、语言、参数、分类和状态由 Provider 决定 |
| 已读回执 | 不是所有渠道都提供 read |
| 送达回执 | 有的只提供接受状态，不代表最终送达 |
| 文件 | 类型、大小、下载有效期和媒体上传流程不同 |
| 消息编辑或撤回 | 多数渠道不与本地脱敏等价 |
| 回复引用 | Provider 对引用 ID 和历史范围要求不同 |
| 互动消息 | 按钮、列表、表单、卡片结构不同 |
| 身份 | 电话、Page 用户、Workspace 用户、邮箱或匿名浏览器身份不同 |
| 回声事件 | 部分渠道会回推本系统已发消息 |
| 签名 | Header、算法、时间窗口和原始 Payload 要求不同 |
| 确认响应 | 200、204、Challenge 文本等要求不同 |
| 顺序 | 同一会话回调可能乱序，串行窗口也不同 |

因此，共享 Message 对象只能统一公共语义，不能抹平渠道限制。

## 13. 当前版本的 HTTP 频率限制基线

实际数值可由安装配置调整。对照验收时必须记录生效配置，并按限制维度分别测试。

| 范围 | 默认限制 | 统计维度 |
|---|---:|---|
| 全局请求 | 3000 次/分钟 | IP |
| Super Admin 登录 | 5 次/5 分钟 | IP |
| Super Admin 登录 | 5 次/15 分钟 | 邮箱 |
| 普通登录 | 5 次/5 分钟 | IP |
| 普通登录 | 10 次/15 分钟 | 邮箱 |
| 密码重置 | 5 次/30 分钟 | IP |
| 密码重置 | 5 次/小时 | 邮箱 |
| 重发确认邮件 | 5 次/30 分钟 | IP |
| 重发确认邮件 | 5 次/小时 | 邮箱 |
| MFA 管理 | 5 次/分钟 | IP |
| MFA 登录验证 | 10 次/分钟 | IP 与 MFA Token |
| Account 创建 | 5 次/30 分钟 | IP |
| Widget 创建 Conversation | 6 次/12 小时 | IP |
| Widget 更新 Contact | 60 次/小时 | IP |
| Widget 新页面会话 | 5 次/小时 | IP |
| Transcript | 1000 次/小时 | Account，可配置 |
| Conversation 删除 | 60 次/分钟 | Account，可配置 |
| 文件上传 | 60 次/小时 | Account |
| Contact 搜索 | 100 次/分钟 | Account，可配置 |
| 用户维度报表 | 100 次/分钟 | User |
| 报表 Drilldown | 用户报表上限的十分之一，最低 1 次/分钟 | User |
| Account 维度报表 | 1000 次/分钟 | Account |
| Conversation Meta | 30 次/分钟 | User + Account |

补充规则：

- 健康检查入口不应被普通业务限流阻断；
- 受信任 IP 可按配置跳过部分限制；
- 正式环境是否强制执行以及具体阈值受安装配置影响；
- 多个限制同时适用时，任一先达到都可以返回 429；
- 限制窗口结束后应自动恢复；
- 429 不得产生本应被拒绝的业务副作用；
- 响应应尽可能提供可判断等待时间的信息。

## 14. 客户端重试决策表

| 结果 | 是否立即重试 | 推荐动作 |
|---|---|---|
| 400 | 否 | 修正请求结构 |
| 401 | 否 | 刷新身份或重新登录，只重放安全请求 |
| 403 | 否 | 检查权限、Feature、套餐和归属 |
| 404 | 否 | 检查路径、范围和对象是否已删除 |
| 409 | 否 | 查询对象状态，按冲突类型决定 |
| 422 | 否 | 修正字段或业务条件 |
| 429 | 是，延迟 | 尊重 Retry-After，并保持同一幂等标识 |
| 500 | 有条件 | 只对可去重操作指数退避 |
| 502/503/504 | 有条件 | 先查询结果，再以相同业务标识重试 |
| 网络断开 | 有条件 | 将结果标为未知，先查询后重试 |

## 15. 补偿与人工恢复入口

| 故障对象 | 自动恢复后仍失败 | 人工恢复动作 |
|---|---|---|
| Message | failed | 检查授权、内容和收件人后执行重试 |
| Inbox Provider | unauthorized/error | 重新授权、重新订阅回调、发送测试消息 |
| Agent Bot | Conversation open 或保持 pending | 人工接管，或修复 Bot 后再次触发 |
| Webhook | 单次投递失败 | 接收方按 delivery ID 对账；必要时业务重放 |
| Data Import | failed/partial | 查看失败条目，以新 run_id 重新执行 |
| Captain Document | failed | 修复来源访问后重新同步 |
| Campaign | partial/completed with failures | 导出失败目标，创建新的补发活动 |
| Call Recording | unavailable | 检查 Provider 录音状态并重新获取 |
| OAuth | state/code 无效 | 从授权起点重新发起 |
| Payment | 状态未知 | 以 Provider event/customer/subscription 查询对账 |

人工恢复也必须幂等，不能因为多次点击产生重复 Message、Campaign 或 Import Item。

## 16. 故障事件的最低记录字段

| 字段 | 用途 |
|---|---|
| occurred_at | 故障发生时间 |
| account_id | 账号范围 |
| inbox_id | 渠道范围，如适用 |
| object_type / object_id | 失败业务对象 |
| provider | 外部平台 |
| operation | 发送、回调、同步、导入等动作 |
| attempt | 当前尝试次数 |
| max_attempts | 最大尝试次数 |
| next_retry_at | 下次自动重试时间 |
| error_category | 认证、校验、限流、超时、永久错误等 |
| provider_error_code | 第三方错误码 |
| safe_error_message | 可展示且不泄露密钥的描述 |
| delivery_id / run_id | 去重和追踪标识 |
| final | 是否已进入终态 |
| recovery_action | 重新授权、修正字段、人工重试等 |

不得在错误记录和响应中暴露 access token、refresh token、签名密钥、密码或完整敏感 Payload。

## 17. 必测异常与第三方场景

| 编号 | 场景 | 预期核对结果 |
|---|---|---|
| ETR-01 | 出站 Webhook 超过 5 秒才响应 | 发送方按超时处理；接收方按 delivery ID 去重 |
| ETR-02 | Agent Bot 连续返回 500 | 3 次尝试后按配置 open 或保持 pending |
| ETR-03 | Agent Bot 返回 400 | 不进入 429/500 的自动重试序列 |
| ETR-04 | WhatsApp 同一事件并发到达 | 互斥等待，最终只产生一次副作用 |
| ETR-05 | Instagram 连续占用互斥窗口 | 1、2、3 秒重试后按既定方式继续处理 |
| ETR-06 | 同一入站消息重复推送 10 次 | 只存在一个 Message |
| ETR-07 | read 后收到 delivered | 公共状态不从 read 降为 delivered |
| ETR-08 | Provider 回声早于发送响应 | 合并到原 outgoing Message |
| ETR-09 | Message 发送响应丢失 | 查询外部 ID 后不重复创建 |
| ETR-10 | Provider Token 失效 | 明确渠道错误并指向重新授权 |
| ETR-11 | 达到普通登录 IP 上限 | 窗口内返回 429，窗口后恢复 |
| ETR-12 | 达到 Contact 搜索账号上限 | 只限制该统计范围，不产生搜索副作用 |
| ETR-13 | Intercom Import 遭遇限流 | 1 分钟间隔，最多 5 次重试 |
| ETR-14 | Captain Document 返回永久访问拒绝 | 不按暂时异常持续重试，进入失败 |
| ETR-15 | Call 已终止后收到 ringing | 保持终态，不回退 |
| ETR-16 | 合法未知 Provider 事件 | 按约定确认并记录，不创建错误业务对象 |
| ETR-17 | 签名错误回调 | 拒绝且不产生任何副作用 |
| ETR-18 | 429 带 Retry-After | 按建议时间等待，不立即重放 |
| ETR-19 | 删除 Campaign 时已有外部消息 | 停止新调度，不宣称撤回已发送消息 |
| ETR-20 | 文件发送失败后用户重试 | 复用原 Message 或按明确规则处理，不产生无法解释的重复消息 |

## 18. 一致性判定标准

本分册范围达到一致，必须同时满足：

1. 故障分类一致；
2. 自动重试触发条件、间隔、上限和终态一致；
3. 超时后的“未知结果”处理一致；
4. 去重键、保存范围和有效期满足相同重复事件场景；
5. Message、Conversation、Import、Document、Call 和 Campaign 的最终状态一致；
6. Provider 回声、乱序、未知事件和授权失败的处理一致；
7. 每项频率限制的阈值、窗口和统计维度一致；
8. 错误响应不泄露敏感凭据；
9. 自动失败后的人工恢复动作不会制造重复副作用；
10. 第 17 节场景全部通过。

只在正常网络下比较成功响应，无法证明第三方接入和消息链路一致。
