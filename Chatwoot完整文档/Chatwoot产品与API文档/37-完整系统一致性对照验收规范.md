# 完整系统一致性对照验收规范

> 适用版本：Chatwoot 4.16.0
> 本分册把全部产品、API、字段、状态、权限、并发、异常和第三方行为转换为可重复的对照验收项，用于判断目标系统是否达到约定范围内的完整一致。

## 1. 验收目标

本规范不以“页面相似”“接口成功”或“主要流程可用”作为通过标准，而要求在同一基线下比较：

- 可发现的功能集合；
- HTTP 方法、路径和认证方式；
- 请求字段、默认值、空值和校验结果；
- 响应字段、枚举、分页和错误；
- 对象状态和关联对象变化；
- 实时事件、Webhook 和第三方请求；
- 并发请求的胜负关系和最终状态；
- 异步任务、超时、重试和补偿；
- 角色、Feature、套餐和运行配置；
- 删除、脱敏、解绑和数据生命周期；
- 搜索、报表、导出和审计中的最终表现；
- 历史数据和旧标识的兼容行为。

只有全部强制项通过，且所有允许差异已经登记，才能声明达到本基线的一致性目标。

## 2. 验收前提

开始对照前必须完成 [32-完整系统一致性还原目标与基线](32-完整系统一致性还原目标与基线.md) 的全部基线包，并至少固定：

| 基线 | 必填内容 |
|---|---|
| 版本基线 | Chatwoot 版本、版本形态、构建日期、API 路径清单 |
| 安装配置基线 | 102 个配置的实际值、默认值和敏感值指纹 |
| Account 基线 | Feature、套餐、额度、状态、时区、语言 |
| 身份基线 | Administrator、Agent、Custom Role、Contact、Bot、Platform、Super Admin |
| Inbox 基线 | 每类渠道、工作时间、成员、Provider 版本和授权状态 |
| 数据基线 | 固定 Contact、Conversation、Message、Campaign、Portal、Assistant 等对象 |
| 时间基线 | 当前时钟、时区、夏令时规则和允许误差 |
| 外部环境基线 | Provider 测试账号、模型、回调地址、邮件和文件条件 |
| 频率限制基线 | 每项实际阈值、窗口、统计维度和受信任 IP |
| 允许差异基线 | 差异编号、原因、归一化方式、影响范围和失效日期 |

任一关键基线未知时，相关项目只能标记为“未具备验收条件”，不能标记为通过。

## 3. 对照对象和环境要求

### 3.1 双环境要求

参考系统与目标系统必须：

- 使用同一版本功能基线；
- 具备等价的 Account Feature 和套餐额度；
- 使用同类型 Inbox 和同等级 Provider 测试账号；
- 导入等价的初始数据；
- 使用同一时区和可控制的时间窗口；
- 对外部请求使用可观察的接收端；
- 在每个场景前恢复到明确初始状态；
- 使用不同的真实外部目标，避免双环境互相消费同一事件；
- 对敏感资料进行脱敏，但保持长度、格式和权限等价。

### 3.2 不允许的比较方式

- 在两个环境使用不同 Feature；
- 一侧使用真实 Provider，另一侧直接跳过 Provider；
- 一侧有历史数据，另一侧为空账号；
- 只比较页面截图，不比较对象和事件；
- 只比较 2xx，不比较错误和副作用；
- 在失败后不恢复初始状态就继续下一场景；
- 把时间、随机 ID、签名等未归一化值直接逐字比较；
- 手工修改结果使其看起来相同。

## 4. 单个验收案例的标准格式

每个案例必须包含以下字段：

| 字段 | 说明 |
|---|---|
| case_id | 全局唯一案例编号 |
| feature_id | 对应功能编号，来源于 23 分册 |
| api_action | 方法与路径，来源于 30 分册 |
| purpose | 本案例验证的业务规则 |
| baseline_ids | 使用的版本、配置、Account、Inbox 和 Provider 基线 |
| identities | 发起身份及权限 |
| preconditions | 执行前对象和状态 |
| request | Header、Path、Query、Body 字段值 |
| concurrency | 请求数量、顺序、间隔和并发屏障 |
| clock | 固定时间、时区和允许误差 |
| immediate_expected | 同步响应和立即状态 |
| object_diff_expected | 对象字段与关联变化 |
| event_expected | 实时事件、活动记录和通知 |
| external_expected | Webhook、Provider 或 AI 请求与响应 |
| final_expected | 异步完成后的最终状态 |
| negative_expected | 明确不应发生的副作用 |
| cleanup | 恢复或隔离场景数据的方式 |
| evidence | 请求、响应、对象快照、事件和时间线证据 |
| tolerance | 时间、顺序或 Provider 允许差异 |
| result | pass、fail、blocked、not_applicable |
| difference_id | 若使用允许差异，填写登记编号 |

## 5. 证据包最低要求

每次完整验收必须保存：

1. 基线清单及其生成时间；
2. 每个 API 动作的请求字段和响应结果；
3. 请求前、立即响应后、最终收敛后的对象快照；
4. 关联对象数量和关键字段变化；
5. 实时事件顺序、事件名、关键 Payload 和接收时间；
6. 出站 Webhook 的 Header、Payload、响应和 delivery ID；
7. 入站回调的来源、校验结果、去重键和确认响应；
8. Provider 请求、Provider 状态和外部资源标识；
9. 异步任务的公开状态、尝试次数和最终时间；
10. 搜索、报表、导出和审计的最终结果；
11. 并发案例中每个请求的开始、响应和提交顺序；
12. 失败案例的错误分类、恢复动作和恢复后结果；
13. 所有动态字段的归一化记录；
14. 所有允许差异的批准记录。

没有证据的“人工确认正常”不计为通过。

## 6. 动态字段归一化

| 字段类型 | 归一化方式 | 仍需比较的内容 |
|---|---|---|
| 自动生成 ID | 建立参考对象与目标对象映射 | 唯一性、引用关系、稳定性 |
| created_at/updated_at | 转为同一时区，应用允许时间误差 | 先后顺序、状态对应时间 |
| 签名 | 使用同一算法和密钥重新验证 | 签名可验证、时间窗口正确 |
| 随机 Token | 不逐字比较 | 长度、字符范围、唯一性、有效期 |
| 外部 Provider ID | 建立同类对象映射 | 回调可关联、重复事件可去重 |
| 文件 URL | 比较可访问性、权限、类型、内容指纹 | 过期和删除后的访问结果 |
| 数组顺序 | 仅在接口不承诺顺序时排序比较 | 元素集合和重复项 |
| 浮点报表值 | 使用指标允许误差 | 口径、分母、时区和筛选条件 |
| AI 文本 | 不要求逐字相同，除非固定结果模式 | 结构、语言、安全规则、引用和功能效果 |

归一化只能消除无业务意义的动态差异，不能隐藏缺失字段、错误状态或错误关联。

## 7. 验收层级

| 层级 | 名称 | 核心范围 | 通过含义 |
|---:|---|---|---|
| L1 | 功能目录一致 | 功能、入口、角色、版本形态 | 没有遗漏功能族 |
| L2 | API 契约一致 | 方法、路径、字段、枚举、错误 | 单次调用契约一致 |
| L3 | 业务状态一致 | 状态机、关联变化、事件和生命周期 | 单流程结果一致 |
| L4 | 运行行为一致 | 并发、异步、限流、重试、第三方 | 复杂环境下最终结果一致 |
| L5 | 完整基线一致 | L1–L4 + 历史兼容 + 长周期对照 | 可在固定基线内声明完整一致 |

任何低层未通过，不得把更高层标记为通过。

## 22. 通过、失败和阻断定义

| 结果 | 定义 |
|---|---|
| pass | 实际结果与预期一致，证据完整，无未登记差异 |
| fail | 字段、状态、副作用、顺序、权限、错误或最终状态不一致 |
| blocked | 缺少必要 Provider、权限、配置、时间条件或有效测试数据 |
| not_applicable | 当前版本形态明确不包含该能力，且基线已说明 |

blocked 和 not_applicable 都不等于 pass。

8. 00–42 分册中的全部强制字段、枚举、分页、容量和业务规则均有案例；

## 24. 允许差异的批准条件

差异只有同时满足以下条件才能被允许：

- 不改变业务含义；
- 不降低权限或账号隔离；
- 不泄露敏感信息；
- 不改变状态机和最终数据；
- 不改变外部副作用次数；
- 不影响 API 调用方的正确判断；
- 可以用确定规则归一化；
- 已指定负责人、原因、范围和失效日期；
- 已获得验收方明确批准。

可考虑允许的差异：随机 ID 具体值、毫秒级时间偏差、不承诺顺序的数组顺序、AI 文本措辞。

不得直接允许的差异：少一个事件、多发一条消息、错误权限、错误终态、错误金额、重复联系人、遗漏删除、未授权访问、错误 Provider 请求。

## 25. 缺陷分级

| 等级 | 定义 | 示例 | 是否阻断完整一致 |
|---|---|---|---|
| S0 | 安全、隔离、数据不可逆损坏 | 跨账号读取、密钥泄露、重复扣费 | 是 |
| S1 | 核心业务结果错误 | 消息丢失、重复发送、状态终态错误 | 是 |
| S2 | 重要功能或恢复能力错误 | 导入失败无状态、重新授权无效 | 是 |
| S3 | 契约或体验差异 | 字段默认不同、错误码不同、排序错误 | 是，除非批准差异 |
| S4 | 无业务含义的展示差异 | 不承诺顺序、可归一化时间格式 | 登记后可不阻断 |

所有 S0–S3 必须归零，才能通过本规范。

## 27. 版本变化后的回归规则

版本、Feature、安装配置、Provider 或模型发生变化时，原结论不能自动延续。至少重跑：

- 所有新增或变更路径；
- 相关请求和响应字段；
- 受影响状态机；
- 受影响权限和 Feature；
- 受影响回调、Webhook 和 Provider；
- 所有相邻并发场景；
- 搜索、报表、导出和审计对账；
- 历史数据兼容；
- 已批准差异是否仍成立。

版本未变化但安装配置、套餐或 Provider 版本变化，也必须更新基线并重跑相应范围。

## 28. 一致性声明模板

只有满足第 23 节后，才可使用以下含义的结论：

“目标系统在 Chatwoot 4.16.0、已登记版本形态、Account Feature、安装配置、套餐、Provider、数据和时间基线内，通过全部适用功能、API、状态、权限、并发、异常、第三方与生命周期对照案例；未批准差异为零，达到本规范定义的固定基线内完整一致。”

不得省略“固定基线”范围，也不得把该结论延伸为：

- 对未来版本永久一致；
- 对未配置 Provider 自动一致；
- 对未执行的历史数据迁移自动一致；
- 对所有网络、时区和规模条件自动一致；
- 对文档未覆盖的新能力自动一致。

## 29. 文档覆盖与实际保证的边界

本套文档可以完整描述当前已识别的功能和可验收规则，但“保证一致”还需要实际执行本规范。三者关系为：

| 层次 | 作用 | 单独能否保证一致 |
|---|---|---|
| 功能与 API 文档 | 说明应该具备什么 | 否 |
| 一致性规则与案例 | 说明怎样判断相同 | 否 |
| 基线固定 + 全量执行 + 证据通过 | 证明本次目标系统在该基线内相同 | 是，限定在本次基线 |

因此，文档解决“标准不完整”的问题；全量对照执行解决“是否真的做到”的问题；版本变化后的持续回归解决“以后是否仍然一致”的问题。
