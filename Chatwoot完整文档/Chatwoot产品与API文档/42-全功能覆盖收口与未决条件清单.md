## 4. 未决条件状态定义

| 状态 | 含义 | 是否影响固定基线完整一致 |
|---|---|---:|
| documented | 规则、输入、输出和验收已经写清 | 否 |
| ready | 环境、账号、数据和时间条件已准备 | 否 |
| running | 正在执行或等待时间窗口 | 是，尚不能声明通过 |
| passed | 实际结果与基线一致，证据完整 | 否 |
| failed | 实际结果不一致 | 是 |
| blocked | 缺少账号、权限、配置或外部条件 | 是 |
| not_applicable | 固定版本形态明确不适用 | 否，但必须说明原因 |

## 5. 真实第三方渠道未决清单

每个 Provider、每种 Inbox 至少完成：

| 类别 | 必测内容 | 最低证据 |
|---|---|---|
| 授权 | 成功、取消、state 错误、scope 缺失、Token 过期 | 授权结果、资源 ID、错误和时间 |
| 入站文本 | 新 Contact、新 Conversation、已有 Conversation | 回调、Message、Contact Inbox 和事件 |
| 入站附件 | 图片、音频、视频、文档、位置或渠道支持类型 | 外部 ID、文件字段和下载结果 |
| 出站文本 | sent、delivered、read、failed | Message 状态时间线和 Provider ID |
| 出站附件 | 各支持类型和大小边界 | Provider 请求和最终状态 |
| Template | 同步、批准、拒绝、语言、参数、发送 | Template 状态和 Message |
| 重复 | 同一事件重放 10 次 | 只有一个有效副作用 |
| 乱序 | read 早于 delivered、终态后迟到事件 | 最终状态不错误回退 |
| 回声 | 系统发送消息被 Provider 回推 | 关联原 Message，不创建重复 incoming |
| 重新授权 | 撤销后恢复 | 同一 Inbox 恢复，不新建重复渠道 |
| 限流 | 429 和 Retry-After | 重试时间和无重复副作用 |
| 删除 | Inbox、Message 或 Contact 删除后的外部差异 | 本地结果和不可撤回边界 |

## 8. 并发和故障未决清单

| 场景 | 最低重复要求 | 通过条件 |
|---|---:|---|
| 两个 Agent 同时领取 | 100 轮 | 只有一个最终 assignee |
| 自动分配与人工分配竞争 | 100 轮 | 结果满足明确优先级，无覆盖丢失 |
| 同一 Provider 回调并发 | 100 轮 | 一个 Message 或一个状态副作用 |
| Contact Merge 与入站消息 | 100 轮 | Message 只归属最终 Contact |
| Campaign 调度竞争 | 100 轮 | 只有一个 processing 批次 |
| Document 同步竞争 | 100 轮 | 单一有效同步，不重复知识内容 |
| Call 终态与迟到状态 | 100 轮 | 终态不回退 |
| Webhook 超时后重放 | 100 轮 | delivery 和业务双重去重 |
| 网络断开 | 各创建动作 | 查询后重试，不生成重复对象 |
| 异步处理暂不可用 | 删除、导入、活动、Webhook | 恢复后最终状态可确认 |

## 9. 大数据量未决清单

| 数据规模 | 必测对象 | 核对内容 |
|---:|---|---|
| 1,000 | Contact、Conversation、Message | 分页、排序、重复 ID、总数 |
| 10,000 | Contact、Conversation、Reporting Event | 搜索、筛选、导出和时间范围 |
| 100,000 | Message、Webhook Delivery、Notification 历史 | 限流、收敛和清理 |
| 1,000,000 或基线目标量 | Message Search、Report | 延迟、90 天范围、分段查询和汇总对账 |

规模不是要求每个环境都达到固定数量，而是必须在目标系统计划承载量下执行。目标规模应写入 32 分册基线。

## 10. 历史数据未决清单

至少准备以下历史样本：

- 缺少 available_name 的 User；
- 缺少 sender_type 或 external_source_ids 的 Message；
- 使用 Facebook Page 型 Instagram 的 Inbox；
- 使用旧 WhatsApp Embedded Signup Feature 的 Account；
- 使用 Conversation 历史排序值的请求；
- 缺少设备信息的 Login Session；
- 缺少 SLA、sentiment 或 identity validation 新字段的对象；
- 已关闭 Feature 但保留历史数据的 Account；
- 已迁移 Email Channel；
- 已合并 Contact 和已删除 Message；
- 运行到一半的 Data Import；
- 失败或陈旧的 Captain Document。

每个样本必须验证读取、更新、导出、删除和升级后行为，不得只验证列表可见。

## 13. 证据未决清单

每个适用案例需要同时具备：

- 基线 ID；
- 请求和响应；
- 执行前对象快照；
- 立即结果；
- 最终结果；
- 实时事件；
- Webhook 或 Provider 结果；
- 重试和尝试次数；
- 搜索、报表、导出和审计对账；
- 时间线；
- 允许差异编号，如有；
- 清理结果。

缺少任一关键证据时，案例不能标记 passed。

## 15. 关闭未决条件的顺序

建议按以下顺序执行：

1. 固定版本、Feature、配置、身份、数据和 Provider 基线；
2. 完成无第三方依赖的 API 字段和权限对照；
3. 完成核心 Contact、Conversation、Message 状态对照；
4. 完成自动化、通知、Webhook 和报表副作用对照；
5. 完成全部 Provider 授权、入站、出站和回调；
6. 完成 AI、Plugin、Cloud 和移动端；
7. 完成并发、故障、限流和大数据量；
8. 完成 24 小时、7 天、跨月和时区观察；
9. 修复所有 fail 并重新执行相关相邻场景；
10. 汇总证据并按 37 分册出具最终结论。

## 16. 变更后重新打开的条件

已经 passed 的项目在以下变化后重新标记为 ready，而不是继续沿用旧结论：

- Chatwoot 版本变化；
- Account Feature 变化；
- 安装配置变化；
- 套餐或额度规则变化；
- Provider API Version 变化；
- OAuth Scope 或 App Review 变化；
- Webhook 订阅变化；
- AI Model 或 Endpoint 变化；
- 关键时间、时区或工作时间变化；
- 目标数据规模变化；
- 历史数据导入或迁移；
- 允许差异到期。

## 17. 完整一致关门条件

只有同时满足以下条件，所有未决项才算关闭：

1. 所有适用案例为 passed；
2. fail 为 0；
3. 未解释 blocked 为 0；
4. 未批准差异为 0；
5. 430 条路径和 651 个动作均有证据；
6. 273 个唯一公开字段均至少在一个请求或响应中验证；
7. 68 个 Feature 和 102 个安装配置均有当前值和可用性结果；
8. 15 类第三方入站回调均验证签名、去重和状态；
9. 12 个 Account Webhook 订阅均验证 Payload 和签名；
10. 37 个业务变化名称的适用副作用均已对照；
11. 全部异步结果到达明确终态；
12. 核心并发场景各完成 100 轮；
13. 至少完成一次 24 小时连续观察；
14. 适用的 7 天、跨月和夏令时场景完成；
15. 搜索、报表、导出和审计与主对象最终对账；
16. 最终报告标明固定基线和有效日期。

## 18. 当前可以作出的准确结论

当前可以确认：

- Chatwoot 4.16.0 的已识别产品功能均有文档入口；
- 全部已发现 API 路径和 HTTP 动作均有索引；
- 公开接口唯一字段名称已全部可查询；
- 状态、权限、并发、异常、第三方和生命周期均有验收规则；
- 文档层面的已识别缺口已经完成收口。

当前不能仅凭文档确认：

- 任意目标系统已经实际达到这些规则；
- 未提供真实账号的 Provider 已经通过；
- 尚未到达观察周期的时间场景已经通过；
- 未来版本和未来 Provider 变化自动保持一致。

这一边界不是文档缺少内容，而是“规范完整”和“实际证明”之间的必要区别。
