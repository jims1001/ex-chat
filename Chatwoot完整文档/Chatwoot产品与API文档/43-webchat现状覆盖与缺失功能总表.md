# webchat 现状覆盖与缺失功能总表

> 对照基线：Chatwoot 4.16.0 及本目录 00 至 42 分册
> 目标：明确 webchat 已有能力、可复用能力、缺失能力、补齐优先级和完成判定。
> 边界：本文只描述产品功能、业务规则、接口合同、字段和验收结果，不包含源码或代码实现。

## 1. 结论

webchat 已经具备较完整的传统企业客服中心能力，适合保留为客服工作台、排队分配、CRM、工单、质检和报表底座。它目前不能直接作为 Chatwoot 的完整等价系统，主要缺口集中在国际渠道、统一会话合同、通用自动化、SLA、公开帮助中心、现代 AI、插件平台、开放平台、安全与企业管理。

| 对照层级 | 当前判断 | 说明 |
|---|---|---|
| 网站在线客服 | 基本覆盖 | Widget、访客接入、排队、分配、会话和满意度已形成闭环 |
| 企业客服中心 | 较高覆盖 | CRM、工单、质检、申诉、监控和报表能力较强 |
| Chatwoot 核心客服 | 大部分覆盖 | 联系人、会话、消息和分配存在，但对象、状态和接口合同不同 |
| Chatwoot 全功能 | 部分覆盖 | 多数模块能找到相邻能力，但大量功能只有局部能力或没有统一入口 |
| Chatwoot API 兼容 | 不满足 | 现有接口路径、认证、字段、状态、错误和事件不能直接替换 Chatwoot API |
| 完整一致还原 | 不满足 | 尚未完成全功能补齐、数据迁移、第三方实测和一致性验收 |

## 2. 状态定义

| 状态 | 含义 |
|---|---|
| 已覆盖 | 已形成可使用的主要业务闭环，只需进行合同统一和验收 |
| 部分覆盖 | 已有相邻能力，但缺少关键动作、字段、状态或跨入口一致性 |
| 未覆盖 | 未发现可直接承接目标功能的完整业务能力 |
| 待实测 | 文档或入口存在，但是否在真实环境形成闭环尚未证明 |
| 不适用 | 固定目标范围明确排除，必须记录排除原因和有效期 |

## 3. 必须保留的 webchat 能力

以下能力不是缺口，补齐过程中应继续保留，并纳入统一对象、权限和报表范围。

### 3.1 客服接待

- 网站聊天窗口和移动端聊天；
- 访客身份传递、咨询前信息收集和离线留言；
- 客服在线、就绪、忙碌、离线等状态；
- 技能组、接待组、并发接待上限和排队；
- 空闲优先、轮转分配和历史客服优先；
- 人工领取、转接、结束、断线恢复和超时处理；
- 文本、图片、语音、文件、商品等消息；
- 会话历史、在线访客、现场监控和服务汇总。

### 3.2 客户和运营

- 客户资料、客户关系、分类和自定义信息；
- 标签、黑名单、敏感词和快捷回复；
- 满意度评价、服务主题和会话分类；
- 客户、会话和报表导入导出；
- 站内通知、短信通知和部分移动推送。

### 3.3 业务管理

- 工单、工单流程、处理记录和评论；
- 质检、质检标签、自动抽检、申诉和复核；
- 客服绩效、排队、渠道、访客、满意度和质检报表；
- 自定义报表设计、发布和导出；
- 多租户、组织、角色、权限和客服账号；
- 动态令牌、IP 白名单、登录审批、密码周期和自动锁定。

### 3.4 传统机器人

- 知识分类、知识问答、批量导入导出；
- 关键词、相似问题、热点问题和多轮问答；
- 场景流程、未命中转人工和答案评价；
- 外部机器人地址、外部知识查询和业务动作；
- 机器人触发工单、短信或转人工。

## 5. 核心对象补齐范围

### 5.1 需要统一的主对象

| 目标对象 | 业务含义 | webchat 可承接内容 | 需要新增的语义 |
|---|---|---|---|
| Account | 租户和数据边界 | 租户、组织标识 | 时区、语言、Feature、设置、套餐和容量 |
| User | 登录主体 | 系统用户、客服账号 | 多账号成员关系、统一 Profile、设备会话和 MFA |
| Team | 会话分配团队 | 部门、接待组、技能组 | 成员关系、自动分配开关和团队报表标识 |
| Inbox | 一条客户渠道或业务入口 | 网站渠道、微信账号等 | 渠道类型、健康状态、成员、工作时间和授权状态 |
| Contact | 统一客户主体 | 客户、联系人、访客 | identifier、邮箱、电话、公司、自定义属性和合并状态 |
| ContactInbox | 客户在某渠道中的身份 | 访客标识、微信身份 | inbox_id、source_id、验证状态和唯一范围 |
| Conversation | 一次客户服务会话 | 服务记录、排队记录 | status、priority、snoozed_until、team、assignee 和 participant |
| Message | 会话内消息或活动 | 聊天消息、系统消息 | private、delivery status、external ID、引用、失败和重试 |
| Attachment | 消息附件 | 图片、语音和文件 | 类型、大小、下载状态、来源和安全扫描状态 |
| Assignment Policy | 自动分配规则 | 现有排队和分配配置 | 规则名称、顺序、优先级、适用 Inbox 和启停状态 |
| Automation Rule | 自动化规则 | 现有超时和机器人规则 | 事件、条件树、动作、执行顺序、失败和防循环 |
| SLA Policy | 服务承诺 | 响应超时监控 | 首次响应、下一次响应、解决时限和违约结果 |
| Assistant | AI 助手 | 机器人实例 | Model、知识、场景、工具、Inbox 绑定和安全规则 |
| Integration App | 可安装扩展 | 定点外部地址 | 能力声明、授权、安装实例、状态和事件订阅 |

### 5.2 对象关系要求

1. 所有业务对象必须明确属于一个 Account；
2. Inbox 必须属于 Account，并声明唯一渠道类型；
3. Contact 可以拥有多个 ContactInbox，但同一 Inbox 下的 source_id 必须唯一；
4. Conversation 必须同时关联 Inbox、Contact 和 ContactInbox；
5. Message 必须属于 Conversation，并保留发送者、方向和渠道外部标识；
6. Team、Agent 和 Bot 的分配必须受 Account 和 Inbox 成员关系限制；
7. Assistant、Automation、SLA、Webhook 和 Plugin 安装实例不得跨 Account 读取或修改资源；
8. 删除或合并对象时，历史消息、报表、审计和第三方关联必须有明确保留规则。

## 6. 接口兼容目标

### 6.1 接口类型

| 接口类型 | 目标用途 | 主要身份 |
|---|---|---|
| Account API | 工作台、账号管理和业务操作 | Account 成员 Token |
| Widget API | 网站聊天窗口 | Widget 会话身份 |
| Public API | 自建客户界面和外部客户系统 | Inbox 与 Contact 公开身份 |
| Platform API | 多租户平台控制面 | Platform App Token |
| Webhook | 向外部系统推送业务变化 | 签名和订阅配置 |
| Provider Callback | 接收外部渠道状态和消息 | Provider 签名或校验信息 |
| Realtime | 工作台和客户侧即时更新 | pubsub_token 或账号订阅身份 |

### 6.2 兼容原则

- 新合同以 00 至 42 分册记录的 Chatwoot 4.16.0 路径、字段和状态为基线；
- 现有 webchat 接口在迁移期可保留为旧入口，但不得产生与新入口不同的业务结果；
- 相同业务动作经不同入口执行时，主对象、事件、报表和审计结果必须一致；
- 认证身份不能混用，Widget 身份不得访问 Account 管理资源；
- 列表必须有稳定分页、排序、筛选和容量上限；
- 创建动作必须具备幂等判定，重复请求不能生成重复客户、会话或消息；
- 第三方发送成功与接口已接受请求必须使用不同状态表达；
- 异步动作必须返回可查询状态，并最终进入成功、失败或取消终态。

接口在补齐清单中分为三类：baseline 表示 30 分册已经记录的 Chatwoot 公开路径；extension 表示为 webchat 补齐运行管理而新增的目标合同；legacy_alias 表示迁移期保留的 webchat 旧入口。没有明确标记为 extension 的公开路径必须与 30 分册一致；运行记录、诊断或验收要求不能自动推导出一个不存在的公开接口。

## 7. 优先级定义

| 优先级 | 范围 | 关门条件 |
|---|---|---|
| P0 | 统一对象、核心接口、租户隔离、会话消息、分配、实时事件 | 网站客服和既有业务在新合同下完整可用，旧数据可读取 |
| P1 | 国际渠道、自动化、SLA、AI、Webhook 和插件 | 关键扩展能力形成业务闭环，失败和重试可确认 |
| P2 | 帮助中心、Platform API、企业安全、移动推送和高级集成 | 管理、客户自助和多端体验完整 |
| P3 | Cloud 计费、套餐、迁移和长期优化 | 套餐与额度准确，长周期和大规模测试通过 |

## 8. 不应重复建设的能力

- 不重新建立第二套客服账号、组织、工单、质检或报表体系；
- 不把每个渠道做成互不关联的客户和会话数据；
- 不为每个外部机器人分别建立独立授权、日志和重试规则；
- 不将快捷回复当作 Macro，将超时配置当作通用自动化，将知识库搜索当作完整 AI；
- 不因为存在日志页面就声明完整审计，不因为存在外部地址就声明插件平台；
- 不因为字段名称相似就声明 API 兼容，必须同时核对路径、身份、状态、错误和副作用。

## 9. 补齐后的完成判定

只有同时满足以下条件，才可以声明 webchat 已达到本套功能基线：

1. 43 至 47 分册列出的适用功能均有可用入口；
2. 核心对象关系和租户边界与本分册一致；
3. 00 至 42 分册的适用 API、字段、状态和错误均已映射；
4. 现有客服、CRM、工单、质检和报表能力没有回退；
5. 新旧入口对相同动作产生一致结果；
6. 全部第三方渠道完成授权、入站、出站、回调、重试和恢复验证；
7. AI 与插件完成权限、额度、失败、超时和副作用验证；
8. 48 分册的核心、并发、异常、数据、时间和兼容验收全部通过；
9. fail 为 0，未解释 blocked 为 0，未批准差异为 0；
10. 最终报告明确版本、配置、Feature、Provider 和有效日期。
