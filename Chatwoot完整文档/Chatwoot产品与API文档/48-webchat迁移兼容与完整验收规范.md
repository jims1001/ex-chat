# webchat 迁移、兼容与完整验收规范

> 对照基线：30 至 42 分册以及 43 至 47 分册
> 目标：规定 webchat 补齐过程的阶段、数据映射、兼容策略、验收证据和完整一致关门条件。
> 边界：本文不描述代码任务，只描述业务交付物、数据结果、接口结果和通过标准。

## 1. 最终目标

补齐完成后的系统应同时满足两项要求：

1. webchat 现有网站客服、微信、CRM、工单、质检、申诉和报表能力不回退；
2. 00 至 42 分册中被确定为适用的 Chatwoot 功能、API、字段、状态、事件和一致性规则全部通过验证。

“页面存在”“接口返回成功”或“主要流程能使用”都不能单独证明完整一致。最终结果必须同时覆盖权限、字段、状态、副作用、并发、失败恢复、第三方、历史数据和长周期行为。

## 2. 补齐阶段

| 阶段 | 目标 | 主要范围 | 进入下一阶段条件 |
|---|---|---|---|
| P0-1 基线固定 | 固定当前 webchat 与目标 Chatwoot 基线 | 版本、配置、租户、账号、渠道、数据和外部依赖 | 基线清单已签定，无未解释变化 |
| P0-2 核心对象 | 建立统一 Account、Inbox、Contact、Conversation、Message | 租户、客户、会话、消息、附件、分配和实时事件 | 网站客服核心闭环和历史读取通过 |
| P0-3 接口兼容 | 建立 Account、Widget、Public 和兼容入口 | 认证、分页、错误、幂等、新旧入口一致性 | 核心 API 和字段对照通过 |
| P1-1 运营能力 | 补齐分配策略、自动化、Macro、通知和 SLA | Assignment Policy、Automation、Macro、Notification、SLA | 核心运营副作用和报表对账通过 |
| P1-2 渠道 | 补齐适用国际渠道和 Provider 生命周期 | Email、WhatsApp、Meta、Telegram、LINE、TikTok、X、Twilio | 每个适用渠道端到端通过 |
| P1-3 AI 与插件 | 补齐 Provider、Assistant、Copilot、Tool、App 和 Webhook | AI、知识文档、插件、集成和 Bot | 权限、额度、失败和副作用通过 |
| P2 企业与客户端 | 补齐 SSO、审计、Platform、Help Center 和移动端 | SAML、OAuth、Audit、Platform、Portal、Push | 企业和多端场景通过 |
| P3 Cloud 与长期验证 | 补齐套餐、额度、计费、迁移和长期稳定性 | Feature、Billing、Migration、大数据量和长周期 | 全部关门条件满足 |

阶段可以细分交付，但后续阶段不能绕过前一阶段的对象和权限基线另建独立数据体系。

## 5. 数据唯一与合并规则

### 5.1 Contact

联系人匹配按明确优先级执行：稳定 identifier → 同一 Inbox 的 source_id → 已验证电话 → 已验证邮箱 → 人工确认。姓名、IP、设备指纹或未验证联系方式不能单独触发自动合并。

合并后：

- 所有 ContactInbox、Conversation、Message、工单、质检、标签和备注归属最终 Contact；
- 冲突字段保留选择结果和原值记录；
- Provider 回调继续能通过原 source_id 找到最终 Contact；
- 被合并 Contact 不再作为活动主体，但保留重定向和审计；
- 合并操作重复提交不得再次产生副作用。

### 5.2 Conversation

历史服务记录转换 Conversation 时，以 Account、Inbox、Contact、开始时间和原服务标识形成稳定映射。一个原服务记录不能生成多个活动会话。无法判断 open 或 resolved 的历史记录默认按明确迁移规则归类并记录原因。

### 5.3 Message

Message 使用原消息标识、Provider 标识或迁移稳定键去重。迁移不得改变原始时间、方向、发送者和正文。缺少发送状态的历史消息标记为 unknown_legacy 或映射到允许的历史状态，不伪造 delivered 或 read。

## 6. 旧接口兼容

### 6.1 兼容期原则

- 旧入口可以继续使用，但所有写动作必须进入同一业务对象和状态规则；
- 旧入口响应可保留原字段，同时提供新对象标识或映射入口；
- 新入口上线后，旧入口不得形成第二套 Contact、Conversation 或 Message；
- 旧入口废止前必须公布替代路径、字段映射、错误差异和截止时间；
- 关键旧入口在兼容期内必须纳入新旧双入口一致性测试。

### 6.2 兼容状态

| 状态 | 含义 |
|---|---|
| active | 继续支持且行为与新合同一致 |
| deprecated | 仍可使用，已经公布替代入口和截止时间 |
| read_only | 只允许历史读取，不允许新写入 |
| removed | 已停止，返回稳定迁移说明 |

### 6.3 新旧入口对账

相同业务动作至少核对：

- 主对象 ID 和最终字段；
- 状态变化和活动消息；
- 实时事件；
- Webhook 和 Provider 结果；
- 通知；
- 自动化和 Bot/Assistant；
- 搜索、报表和导出；
- 审计；
- 失败、重试和幂等结果。

## 7. 历史数据验收

至少准备以下样本：

- 同一客户拥有网站、微信、电话或多个历史身份；
- 缺少邮箱、电话、姓名或统一标识的访客；
- 已结束、排队中、转接中、异常断开的历史服务；
- 文本、图片、语音、文件、商品和系统消息；
- 发送失败、缺少 Provider 状态或重复回调的消息；
- 带满意度、质检、申诉、工单和标签的会话；
- 已删除、停用、锁定或离职客服的历史会话；
- 已停用渠道和过期授权的历史消息；
- 多语言知识、机器人场景和人工纠正内容；
- 大批量导入、导出和报表历史。

每个样本验证读取、搜索、筛选、导出、关联、权限和后续更新，不得只确认列表存在。

## 9. 第三方渠道验收

每个适用渠道独立完成：

1. 授权成功、取消、错误 state、Scope 不足和 Token 过期；
2. 文本、图片、音频、视频、文件、位置和渠道支持的互动类型；
3. 新 Contact、新 Conversation 和已有 Conversation；
4. 出站 sent、delivered、read、failed；
5. Template 同步、审核、语言、参数和发送；
6. 重复、乱序、回声和迟到状态；
7. 429、Retry-After、5xx、超时、断网和恢复；
8. 重新授权不重复创建 Inbox；
9. 删除、停用和外部不可撤回差异；
10. 搜索、报表、Webhook、审计和导出对账。

## 12. 故障与恢复验收

至少覆盖：

- 数据库暂不可用；
- 缓存或搜索暂不可用；
- 实时连接断开和重连；
- 文件存储上传或下载失败；
- Provider 认证失败、限流、5xx 和超时；
- Webhook 接收方不可用；
- AI Provider 或 Tool 不可用；
- 异步任务执行中重启；
- 批量导入、迁移或删除中断；
- 网络结果未知后重复提交。

恢复后必须确认主对象、事件、Webhook、搜索、报表、导出和审计最终一致。不能只确认服务恢复响应。

## 16. 结果状态

| 状态 | 含义 |
|---|---|
| documented | 规则和案例已经写清 |
| ready | 环境、账号、数据和权限已准备 |
| running | 正在执行或等待观察窗口 |
| passed | 实际结果与固定基线一致且证据完整 |
| failed | 结果不一致 |
| blocked | 缺少外部账号、权限、配置或环境条件 |
| not_applicable | 固定目标明确不适用，并已说明原因 |

文档完成只能把项目推进到 documented；没有真实执行和证据，不能直接标记 passed。

## 17. 允许差异

允许差异必须记录：差异编号、功能、原因、影响范围、替代行为、风险、批准状态、开始时间、到期时间和重新评估条件。

以下项目不能仅通过允许差异规避：

- 跨 Account 数据泄露；
- 认证绕过或权限提升；
- 重复支付、重复 Tool 副作用或重复外部订单；
- 消息、客户、会话、工单或质检核心数据丢失；
- 审计敏感信息泄露；
- 无法确认的迁移差异；
- 未告知客户的消息重复发送。

## 18. 回退和恢复

每个阶段必须具备：

- 变更前可恢复备份；
- 新旧对象 ID 映射；
