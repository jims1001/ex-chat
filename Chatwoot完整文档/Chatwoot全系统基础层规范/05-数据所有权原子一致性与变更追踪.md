# 数据所有权、原子一致性与变更追踪

## 1. 数据所有权

每个对象必须登记唯一权威模块。权威模块拥有：

- 对象正文、状态机和唯一约束；
- 创建、更新、状态、关系、归档、恢复和删除 Command；
- object_version 和业务时间；
- 本地原子变更记录；
- 权威 Query 和事实 Event；
- 数据迁移、补偿和对账规则。

其他模块只能保存稳定引用、受控快照或可重建投影，不能修改权威事实。

## 2. 数据类型

| 类型 | 是否权威 | 规则 |
|---|---:|---|
| 领域对象 | 是 | 只由一个模块拥有 |
| 关系对象 | 是 | 明确一个关系所有者 |
| Local Change Journal | 变更原子机制 | 随权威模块短期保存，用于投递和恢复 |
| Data Change Ledger | 审计权威 | AUD 集中只追加保存，不是业务对象来源 |
| Search/Report/Realtime 投影 | 否 | 可重建，标记版本和新鲜度 |
| 缓存 | 否 | 失效后回到权威 Query |
| 兼容视图 | 否 | 映射现有权威数据，不保存第二事实 |
| 插件私有数据 | 仅插件范围 | 不得复制核心对象成为替代来源 |
| ORC 流程状态 | 仅流程权威 | 不拥有领域对象正文 |

## 3. 原子边界

单模块每次写入至少原子完成：

1. 权威对象或关系变化；
2. object_version 增加；
3. Local Change Journal 写入；
4. 必要的业务唯一收据或幂等结果。

Local Journal 失败时整个业务变化失败。集中 AUD、Webhook、通知、搜索或报表失败时，已经完成的业务事实不回滚，由本地记录和事件机制重试。

## 4. Data Change 最低合同

每次实际变化至少记录：

- change_id、schema_version、source_module；
- account_id、object_type、object_id；
- object_version_before、object_version_after；
- action、changed_fields、受控 before/after/diff；
- actor_type、actor_id、source_type、source_id；
- request_id、command_id、event_id；
- correlation_id、causation_id；
- occurred_at、recorded_at、ingested_at；
- data_classification、retention_class、integrity_hash。

未发生实际变化时返回 no_change，不伪造 Data Change。权限、校验和登录失败进入安全或操作记录。

## 5. 变更动作

统一动作包括：create、update、status_change、add_relation、remove_relation、replace_set、merge、split、archive、restore、soft_delete、hard_delete、redact、migrate、compensate、correct_log。

模块不得使用无法跨模块理解的同义动作代替公共动作；领域细节通过 reason、changed_fields 和 metadata 表达。

## 6. 并发

| 场景 | 处理 |
|---|---|
| 同对象同字段更新 | 使用 expected_version、锁定或明确后写规则 |
| 不同字段更新 | 按局部更新合同合并，整体替换必须明确 |
| 创建竞争 | 使用业务唯一键和幂等收据收敛 |
| 集合并发 | 使用 add/remove/replace_set 语义和集合版本 |
| Provider 回调乱序 | 按允许状态机、外部序列和 object_version 判断 |
| 异步任务重复 | 以任务目标、状态和唯一键保证一次有效副作用 |
| 支付/额度竞争 | 预留、消费、释放和冲正使用权威原子规则 |

每个成功版本必须恰好有一条对应 Change；失败并发不能产生虚假版本。

## 7. 跨模块一致性

跨模块不使用共享业务事务，采用 ORC、幂等 Command、Event 和显式补偿：

1. 每个模块独立提交自己的事实和 Change；
2. 全部步骤共享 correlation_id；
3. causation_id 指向直接原因；
4. ORC 保存步骤和终态；
5. 失败后执行新的补偿 Command；
6. 已发生事实和原 Change 永久保留；
7. 查询可以按 correlation_id 组合完整时间线。

## 8. 投影一致性

RPT、SRH、RTM、缓存和外部投递允许最终一致，但必须：

- 按 event_id 幂等；
- 使用 object_version 发现重复和断层；
- 返回 projection_version 和新鲜度；
- 支持补读或全量重建；
- 不反向修改权威对象；
- 不被权威模块同步依赖为完成条件。

## 9. 批量、导入和迁移

批量操作必须同时拥有批次记录和每个实际变化对象的 Change。成功、失败、跳过和 no_change 分开统计。迁移通过公开 Command 写入，保留 mapping_version、legacy_id、target_id、batch、checkpoint 和 change_id；不得直接修改目标模块内部数据。

## 10. 对账

| 对账 | 通过条件 |
|---|---|
| Local committed vs AUD ingested | 数量和 change_id 一致，允许受控短时延迟 |
| object_version vs Change | 每个成功版本连续且可定位 |
| Event vs Change | 数据变化事件引用同一 change_id |
| Projection vs Authority | 在允许延迟后字段和版本一致 |
| Batch vs Objects | 总数等于成功、失败、跳过和未变化之和 |
| Migration vs Mapping | 所有目标对象和关系可由映射定位 |
| Delete vs Copies | 投影、索引、导出和插件副本按政策完成 |

## 11. 验收

- [ ] 每个对象和关系只有一个所有者；
- [ ] 跨模块内部存储访问为 0；
- [ ] 业务变化和 Local Journal 原子完成；
- [ ] 每个成功 object_version 有唯一 change_id；
- [ ] 重复、并发、乱序和超时没有重复事实；
- [ ] 投影可重建且不会反向成为权威；
- [ ] 批量和迁移能追踪到单对象；
- [ ] 所有对账差异为 0 或有受控待投递状态。
