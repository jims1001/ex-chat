# 可靠性、故障隔离、限流、监控、恢复与容量

## 1. 可靠性目标

每个动作必须明确：主结果、异步副作用、超时、重试、幂等、失败终态、降级、补偿、恢复和对账。不能只描述正常流程。

## 2. 失败分类

| 分类 | 示例 | 通用处理 |
|---|---|---|
| validation | 字段、状态、唯一约束 | 永久拒绝，修正输入 |
| authentication | Token、Session、签名无效 | 不重试，重新认证 |
| authorization | Role、Scope、对象范围不足 | 不重试，不泄露对象 |
| conflict | object_version、并发、唯一竞争 | 重新读取后决定 |
| rate_limit/quota | 频率、并发、额度 | 按恢复时间重试或等待周期 |
| dependency_temporary | 网络、节点、Provider 暂时不可用 | 只对幂等安全动作退避重试 |
| dependency_permanent | 授权撤销、模板拒绝、Scope 缺失 | 停止重试并进入修复流程 |
| result_unknown | 外部可能已成功但响应丢失 | 先 Query 或等待回调 |
| integrity | 日志断层、摘要冲突、无记录变化 | 隔离写入口并调查 |
| capacity | 队列、存储、连接、导出超限 | 降低入口、暂停批量并扩容 |

## 3. 超时

超时分为入口截止、模块调用、外部 Provider、异步任务、流程等待和总业务期限。每层必须明确：

- 开始和截止时间；
- 超时是否表示未执行、结果未知或已进入后台；
- 可使用的结果 Query；
- 是否允许重试及复用哪个幂等关系；
- 何时进入补偿或人工处理；
- 面向外部的错误和下一步。

## 4. 重试

- 只重试明确的暂时错误；
- 使用延迟、随机偏移、次数和总期限；
- 不对认证、权限、校验和永久 Provider 拒绝自动重试；
- 不可逆动作必须有幂等键和结果查询；
- 重试沿用 correlation_id 和业务幂等关系，每次尝试使用独立 attempt/delivery_id；
- 达到上限进入失败、死信或人工状态，不无限循环；
- 恢复后按顺序补投并执行对账。

## 5. 故障隔离

| 故障 | 允许继续 | 必须停止或限制 |
|---|---|---|
| Search/Report 延迟 | 核心写入和权威 Query | 依赖最新投影的导出 |
| Realtime 不可用 | REST 查询和业务写入 | 实时投递 |
| Webhook/Notification 失败 | 已完成业务事实 | 对应外部投递 |
| AI/Plugin 不可用 | 人工客服、核心会话消息 | 对应智能或扩展动作 |
| 单个 Provider 不可用 | 其他 Inbox 和渠道 | 该连接的新外部动作 |
| Central Audit 不可用 | Local Journal 可靠时受控继续 | 达到积压水位后的批量和高风险写入 |
| Local Journal 不可用 | 读取 | 所有受影响数据写入 |
| ORC 不可用 | 单模块动作和已有可读状态 | 新跨模块流程 |
| IAM/TEN 核心判定不可用 | 公共静态读取按策略 | 需要新授权的业务写入 |

## 6. 限流、背压和优先级

限流维度：身份、IP/来源、Account、接口族、对象、Provider、插件安装、模型、异步队列和导出。背压顺序默认：

1. 限制大范围导出和重建；
2. 暂停低优先级同步和历史补算；
3. 限制批量、导入和迁移；
4. 限制非关键自动化、AI 和插件动作；
5. 保留身份、安全、客户入站、人工消息和必要查询；
6. Local Journal 或完整性失败时停止相关写入。

## 7. 运行状态

每个模块至少提供：

- availability：available、degraded、unavailable；
- dependency_status：依赖类别和影响范围；
- queue/backlog：数量、最老年龄和水位；
- error_rate 和 latency；
- version、contract_version、foundation_version；
- last_success、last_failure 和恢复时间；
- projection/index/checkpoint 新鲜度；
- 当前降级、限流和暂停策略。

运行状态不能包含 Secret、客户正文或未经授权的内部地址。

## 8. 告警和对账

| 周期 | 内容 |
|---|---|
| 实时 | 认证攻击、摘要冲突、Payload 冲突、无记录变化 |
| 分钟 | 队列、Local pending、Provider/Plugin 失败和延迟 |
| 小时 | committed/ingested、Event/Projection 数量和失败分布 |
| 日 | object_version、完整性链、索引、保留和副本清理 |
| 发布前 | 合同、Registry、依赖、容量和回归 |
| 迁移后 | 数量、关系、内容、权限、Change 和映射 |
| 灾备演练 | 备份、恢复、补投、重建和完整性验证 |

安全、完整性和未记录变化不能被永久静默。告警抑制必须有范围、原因、开始、到期和批准。

## 9. 容量

每个模块评估：对象量、写入峰值、事件放大倍数、Payload 大小、附件、索引、保留周期、队列、并发连接、外部配额、批量规模、导出和增长率。

容量边界必须形成：软水位、硬水位、自动扩缩、拒绝顺序、恢复阈值、预估时间和告警。不能等到存储耗尽后才决定停止哪些动作。

## 10. 恢复

统一恢复顺序：

1. 确定开始时间、影响模块、Account 和对象；
2. 保护权威数据、Local Journal、Ledger 和原始回执；
3. 阻止继续扩大不一致；
4. 修复身份、合同、容量、网络、Provider 或存储问题；
5. 按幂等键、source_sequence 和 object_version 补投；
6. 重建可重建索引和投影；
7. 对账对象、Change、Event、流程、外部回执和副本；
8. 处理无法自动恢复的未知或不可逆结果；
9. 逐级解除限制；
10. 记录事件、根因、预防规则和重验范围。

## 11. 灾难恢复

必须冻结备份范围、恢复点目标、恢复时间目标、数据位置、密钥可用性和恢复顺序。恢复后先验证身份与配置，再验证权威对象和账本，最后重建搜索、报表、缓存和实时游标。

## 12. 验收

- [ ] 每类失败有重试、停止、补偿或人工结果；
- [ ] 超时不会制造重复业务和外部副作用；
- [ ] 可选模块故障不拖垮核心客服；
- [ ] Local Journal 失败时没有无记录写入；
- [ ] 限流、背压和容量水位可执行；
- [ ] 告警、对账、恢复和灾备有证据；
- [ ] 恢复后无丢失、重复、版本断层和永久错误状态。
