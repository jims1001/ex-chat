# 自动化规则、宏与统一动作能力合同

## 1. 定位

自动化和宏不是基础层公共业务模块，但它们必须共同使用基础层提供的统一动作能力合同。本分册规定 AUT、OPS、ORC、API 和目标业务模块如何协作，避免自动化、宏和手工入口分别实现三套业务动作。

## 2. 功能边界

| 能力 | 触发方式 | 权威模块 | 作用 |
|---|---|---|---|
| Automation Rule | 业务 Event、时间或计划触发 | AUT | 判断条件并按规则执行动作 |
| Macro | Account 成员人工选择并执行 | OPS | 对一个或多个会话执行预定义动作组合 |
| Canned Response | 人工搜索、插入和确认 | OPS | 提供可复用文本，不直接发送消息 |
| Campaign | 计划、受众或持续条件触发 | OPS | 对多个目标建立可追踪发送任务 |
| Action Capability | AUT、OPS、AIC、插件或 API 调用 | 各目标业务模块 | 执行真正的分配、消息、状态、标签等业务动作 |
| Multi-step Process | 两个以上模块或外部步骤 | ORC | 管理步骤、等待、失败、补偿和整体终态 |

AUT 不拥有 Conversation、Message、Assignment 或 Notification；OPS 不拥有这些目标对象。目标模块始终重新验证权限、Account、对象状态和字段。

## 3. 设计思路

1. 触发、条件、动作和结果分开；
2. 自动化与宏复用同一 Action Capability，不复制目标业务规则；
3. 每次执行冻结规则或宏版本，运行中更新不改变既有执行；
4. 每个动作都有目标模块、参数合同、权限、幂等、超时和结果 Query；
5. 单模块动作直接发 Command，多模块或外部动作按 L0 Process Contract 提交流程意图，由 ORC 消费；AUT 和 OPS 不读取 ORC 内部状态；
6. 自动化使用系统执行身份，但不能绕过 Account 和目标对象权限；
7. 宏使用实际操作者身份和权限快照；
8. 所有动作结果按单目标、单动作保存，不能只给整体成功；
9. 自动化防循环由事件因果、执行键、递归深度和动作抑制共同保证；
10. 规则、宏、执行和目标对象变化全部进入 Data Change Ledger。

## 4. 数据所有权

| 模块 | 权威对象 | 不拥有 |
|---|---|---|
| AUT | AutomationRule、RuleVersion、AutomationExecution、ActionExecution、TriggerCheckpoint | 目标业务对象、Macro、Campaign |
| OPS | Macro、MacroVersion、MacroExecution、CannedResponse、Campaign、CampaignRecipient | Conversation、Message、Assignment、Notification Delivery |
| ORC | Process、Step、Compensation、Correlation | 规则、宏和目标对象正文 |
| 各业务模块 | 自身对象、状态和 Action Capability | 自动化条件和宏定义 |
| AUD | 变更账本和审计时间线 | 当前规则、宏或目标对象状态 |

每个目标模块拥有自己提供的 Capability Definition 和版本；集中 Action Capability Registry 只是可重建目录，不拥有业务规则、动作结果或业务状态。AUT、OPS、AIC 和 EXT 从目录发现能力，最终仍调用目标模块合同。

## 5. Action Capability 合同

每个可被自动化、宏、AI Tool 或插件调用的动作必须登记：

| 字段 | 说明 |
|---|---|
| capability_id | 稳定动作标识，如 conversation.change_status |
| capability_version | 参数、权限和副作用合同版本 |
| owner_module | 最终执行动作的权威模块 |
| command_type | 对应公开 Command |
| target_types | 允许的目标对象 |
| input_schema | 参数、类型、必填、默认和枚举 |
| allowed_callers | automation、macro、ai、plugin、account_api 等 |
| required_permissions | 操作者或系统身份必须具备的权限 |
| required_features | Feature、套餐、额度或安装配置 |
| idempotency_scope | 执行键的组成和有效期 |
| timeout/result_query | 超时和结果确认方式 |
| retry_policy | 可重试错误、上限和退避 |
| compensation | 允许的补偿或不可逆说明 |
| emitted_events | 成功后发布的事实事件 |
| change_actions | 产生的数据变化动作 |
| data_classes | 输入、输出和日志字段分级 |
| bulk_support | 是否允许批量、最大目标和部分失败规则 |

未进入 Registry 的动作不得被规则、宏、AI 或插件执行。

## 6. Automation Rule 对象

| 字段 | 必填 | 说明 |
|---|---:|---|
| id/account_id | 是 | 规则和 Account 边界 |
| name | 是 | 规则名称 |
| description | 否 | 业务目的和影响范围 |
| event_name | 是 | 触发事件 |
| active | 是 | 是否接受新执行 |
| version | 是 | 规则版本，更新后递增 |
| conditions | 是 | 条件树或条件列表 |
| actions | 是 | 有序动作列表 |
| failure_policy | 是 | stop、continue、compensate 或 manual |
| max_depth | 是 | 最大递归深度 |
| effective_at/expires_at | 否 | 生效与到期时间 |
| created_by/updated_by | 是 | 管理主体 |
| created_at/updated_at | 是 | 生命周期时间 |

创建、更新、复制、启停、归档和删除都生成 Data Change。复制规则必须生成新 ID，默认停用或重新确认，不能与原规则静默同时运行。

## 7. 自动化触发合同

基础触发事件包括 conversation_created、conversation_updated、conversation_opened、conversation_resolved、message_created；扩展事件和时间触发必须进入 Trigger Registry。

触发上下文至少包含：

- event_id、event_type、event_version；
- account_id、object_type、object_id、object_version；
- change_id、correlation_id、causation_id；
- actor/source；
- 允许判断的当前字段和 changed_fields；
- occurred_at、Account timezone；
- automation_depth 和 origin_execution_id。

AUT 只消费已经完成的事实 Event，不能在目标对象提交前提前执行。

## 8. 条件合同

| 字段 | 说明 |
|---|---|
| attribute_key | 允许读取的字段或自定义字段 |
| attribute_source | conversation、message、contact、inbox 等权威 Query |
| value_type | string、number、boolean、enum、time、id、list |
| filter_operator | equal、not_equal、contains、present、range、time 等 |
| values | 比较值 |
| logical_operator | AND、OR；嵌套时必须有明确分组 |
| null_policy | 缺失、null、空字符串和空集合如何判断 |
| case/locale_policy | 文本大小写、语言和标准化规则 |
| snapshot_version | 条件判断使用的对象版本 |

条件只能读取公开 Query，不读取目标模块内部数据。字段和操作符不匹配、跨 Account 引用或停用自定义字段时，规则不能启用或执行必须明确失败。

## 9. 自动化执行状态

| 状态 | 含义 |
|---|---|
| received | 已收到触发事件 |
| evaluating | 正在读取上下文和判断条件 |
| skipped | 条件不匹配或已被幂等处理 |
| running | 正在执行动作 |
| waiting | 等待延迟、Provider、ORC 或人工结果 |
| partially_succeeded | 部分动作成功，失败策略允许保留 |
| succeeded | 所有要求动作完成 |
| failed | 无法继续且失败已确定 |
| compensating | 正在执行补偿 |
| cancelled | 规则停用或人工取消允许停止的部分 |
| loop_blocked | 因递归深度或重复因果被阻止 |
| manual_action_required | 需要人工处理 |

execution_key 至少由 rule_id、rule_version、event_id、target_id 和目标版本构成。相同执行键只能产生一个有效执行。

## 10. 自动化执行流程

1. AUT 接收标准 Event；
2. 查找当前 Account、event_name 和有效时间内的 active RuleVersion；
3. 建立 execution_key 并进行幂等检查；
4. 检查 causation 链、automation_depth 和已执行规则；
5. 通过公开 Query 构建只读触发上下文；
6. 按冻结条件树求值并记录匹配结果；
7. 未匹配则进入 skipped；
8. 按顺序解析 Action Capability；
9. 以 automation actor、rule_id、execution_id、correlation_id 调用目标 Command，或提交标准 Process Intent 并等待公开 Process Signal；
10. 每个动作记录 accepted、succeeded、failed、skipped、result_unknown 或 compensated；
11. 按 failure_policy 继续、停止、补偿或转人工；
12. 形成执行终态并发布 automation.execution_completed/failed；
13. AUD、RPT 和运行监控消费结果；
14. 新产生的 Event 保留 origin_execution_id 和递归深度。

## 11. 防循环

必须联合使用：

- event_id + rule_id + version 执行幂等；
- correlation_id、causation_id 和 origin_execution_id；
- automation_depth 和最大深度；
- 同一规则禁止对同一对象版本重复执行；
- conversation_updated 仅在登记字段真实变化时触发；
- 规则动作产生的 Event 标记自动化来源；
- send_message 规则区分 incoming、outgoing、private 和 activity；
- 两条规则互相触发时检测重复因果路径；
- 达到阈值进入 loop_blocked 并告警，不静默无限执行。

## 12. Macro 对象与接口字段

| 字段 | 必填 | 说明 |
|---|---:|---|
| id/account_id | 是 | Macro 和 Account 边界 |
| name | 是 | 名称 |
| description | 否 | 适用场景和影响 |
| version | 是 | 更新后递增，执行冻结版本 |
| actions | 是 | 有序 Action Capability 列表 |
| visibility | 是 | personal、team 或 global |
| owner_id/team_ids | 按可见性 | 所有者和团队范围 |
| confirmation_policy | 是 | 是否需要执行前预览和确认 |
| bulk_policy | 是 | 是否允许批量和最大目标数 |
| active | 是 | 是否允许新执行 |
| created_by/updated_by | 是 | 管理主体 |

执行请求字段至少包含 macro_id、macro_version、conversation_ids、custom_params、idempotency_key、request_id 和 dry_run/confirm 状态。

## 13. Macro API 动作

| 方法 | 路径 | 功能 |
|---|---|---|
| GET | /api/v1/accounts/{account_id}/macros | 按个人、团队和全局范围查询 |
| POST | /api/v1/accounts/{account_id}/macros | 创建 Macro |
| GET | /api/v1/accounts/{account_id}/macros/{id} | 查询详情和当前版本 |
| PATCH | /api/v1/accounts/{account_id}/macros/{id} | 更新并形成新版本 |
| DELETE | /api/v1/accounts/{account_id}/macros/{id} | 停止新执行并按保留规则处理 |
| POST | /api/v1/accounts/{account_id}/macros/{id}/preview | 对目标会话预览动作、权限和影响 |
| POST | /api/v1/accounts/{account_id}/macros/{id}/execute | 执行单个或多个会话 |
| GET | /api/v1/accounts/{account_id}/macro_executions/{execution_id} | 查询总体和逐目标、逐动作结果 |
| POST | /api/v1/accounts/{account_id}/macro_executions/{execution_id}/cancel | 取消未开始的目标或动作 |

现有接口没有单独 preview 时，可以把预览作为扩展合同，但执行前仍必须重新读取对象、权限和 Action Capability 可用性。

## 14. Macro 执行流程

1. API 验证 Account、实际操作者和 Macro 可见性；
2. 读取并冻结 MacroVersion；
3. 校验目标会话数量、归属和 Inbox 权限；
4. 逐目标预览动作、参数、权限、Feature、状态和不可逆影响；
5. 建立 macro_execution_id 和批次幂等键；
6. 对每个目标建立独立 execution item；
7. 单模块动作调用目标 Command，多动作或跨模块提交标准 Process Intent，由 ORC 编排；
8. 每个动作使用 macro_execution_id、target_id、action_index 组成幂等关系；
9. 记录成功、跳过、失败、结果未知和补偿；
10. 单目标失败不掩盖其他目标结果；
11. 取消只停止未开始动作，不撤销已经完成的不可逆结果；
12. 汇总总体终态并提供逐目标结果查询。

## 15. 快捷回复与 Macro 的区别

Canned Response 只拥有 short_code、content、变量定义、可见性和版本。使用时先解析变量并预览，不自动发送。真正发送仍由 MSG Command 执行，因此快捷回复不会绕过会话、渠道、权限、模板和审计规则。

Macro 是动作组合，可以包含发送消息，但不能把快捷回复的内容模板误当作完整 Macro，也不能让快捷回复直接改变状态、分配或标签。

## 16. 权限

| 操作 | 权限要求 |
|---|---|
| 管理 Automation Rule | Administrator 或明确自动化管理权限 |
| 执行 Automation | 系统执行身份 + Rule 权限范围 + 目标模块再次验证 |
| 管理全局 Macro | Administrator 或 Macro 管理权限 |
| 管理个人 Macro | 当前所有者和 Account 范围 |
| 执行 Macro | Macro 可见 + 操作者对每个目标动作有权限 |
| 批量 Macro | 批量权限、目标上限和高风险确认 |
| 管理快捷回复 | 对应内容管理权限 |
| 执行外部动作 | Provider/Plugin Scope、数据分级和允许域名 |

宏不能因为由管理员创建就让普通执行者继承管理员权限。自动化也不能因为是系统身份就绕过目标模块业务规则。

## 17. 失败、重试和补偿

- 条件 Query 失败：执行进入 waiting 或 failed，不按未知值当作匹配；
- 目标动作校验失败：永久失败，不盲目重试；
- 目标模块暂时不可用：按 Capability 重试策略处理；
- 外部动作超时：按 invocation_id 查询，不重复调用；
- 前项失败：按冻结 failure_policy 决定继续、停止、补偿或人工；
- 规则停用：阻止新执行，运行中的执行按政策继续或取消未开始动作；
- Macro 更新：不改变已经冻结的 MacroExecution；
- 批量执行：每个目标独立终态，总体结果可以部分成功；
- 已发送消息、已触达 Webhook 或已执行不可逆 Tool 不能伪装为回滚。

## 18. 日志和事件

必须追踪：

- Rule/Macro/CannedResponse 创建、版本、启停、可见性和删除；
- AutomationExecution/MacroExecution 的触发、操作者、目标和终态；
- 每个 ActionExecution 的输入摘要、目标 Command、change_id、耗时和错误；
- loop_blocked、权限拒绝、外部结果未知、补偿和人工处理；
- 批量执行的整体记录和单对象 Change；
- restricted 参数按基础层遮蔽，不保存 Secret 或完整敏感正文。

## 19. 扩展点

新增自动化或宏动作必须注册 Action Capability，并声明 owner_module、权限、参数、幂等、失败、补偿、数据分级和版本。插件可以提供 Capability，但必须经过 EXT 安装、Scope、签名、网络和故障隔离；AUT 和 OPS 不直接保存插件 Secret。

新增触发事件必须由权威模块发布标准 Event，并明确可用于条件判断的最小字段。AUT 不允许订阅未登记内部事件。

## 21. 完成判定

- [ ] AUT、OPS 只依赖 L0 Process Contract，不依赖 ORC 内部状态；AUT、OPS、ORC 和目标模块边界唯一且无循环；
- [ ] 自动化与宏复用同一 Action Capability；
- [ ] RuleVersion 和 MacroVersion 在执行开始时冻结；
- [ ] 触发、条件、动作和结果均有稳定合同；
- [ ] 自动化幂等、防循环、递归深度和双规则互触发通过；
- [ ] Macro 单目标、批量、预览、权限和部分失败通过；
- [ ] 目标动作与手工入口使用同一 Command 和业务规则；
- [ ] 每个实际数据变化都有 change_id；
- [ ] 外部动作超时不会重复执行；
- [ ] 快捷回复只负责内容，不绕过 MSG 发送；
- [ ] 新动作和触发扩展点全部登记；
- [ ] Secret 和 restricted 原值泄露为 0。
