# 日志基础层总体架构与分类

> 日志任务：LOG-01。

## 1. 设计目标

日志体系需要同时解决四个问题：

- 谁在什么时间通过什么入口改变了什么数据；
- 变化前后分别是什么，为什么发生，最终是否成功；
- 一次跨模块流程中的全部变化能否串联；
- 日志自身是否完整、可验证、不会泄露敏感信息。

日志体系属于 L0 基础层，不是业务完成后再接入的附加功能。IAM、TEN、CHN、CUS、CON、MSG、RTE、AIC、EXT 等全部模块只能通过统一日志基础合同提交数据变化。

## 2. 基础层结构

日志基础层分为两个平面：

| 平面 | 组成 | 运行要求 |
|---|---|---|
| Local Capture Plane | Change Context、Change Contract、敏感字段策略、Local Change Journal、Publisher | 与每个业务模块共同运行；任何数据写入都必须经过 |
| Central Ledger Plane | AUD Ingestion、Immutable Ledger、Audit Index、Integrity、Archive、Audit API | 独立运行；允许短时不可用，由 Local Journal 保证不丢失 |

依赖方向为：业务模块 → L0 Local Capture Contract；Central Ledger 消费各模块待投递记录。业务模块不反向依赖 Audit API，也不因需要查询日志才能完成自己的业务状态。

Local Capture Plane 不可用时，数据写入必须失败；Central Ledger Plane 暂时不可用时，已经原子保存 Local Journal 的业务写入可以在容量和风险策略允许范围内继续。

## 3. 日志分类

| 类型 | 目的 | 是否记录数据变化 | 权威所有者 |
|---|---|---|---|
| Data Change Ledger | 记录业务对象每次实际变化 | 是，强制 | AUD |
| Business Audit Log | 记录有业务意义的操作和审批 | 引用 change_id | AUD |
| Security Log | 登录、MFA、Token、权限拒绝、异常访问 | 通常不改变业务对象 | IAM/AUD 集中保存 |
| Access Log | 记录敏感查询、导出和高权限读取 | 否 | AUD |
| Integration Delivery Log | Provider、Webhook、插件和推送的投递尝试 | 引用相关 change_id/event_id | EXT/CHN/NTF，AUD 保存审计摘要 |
| Process Log | 跨模块流程步骤、等待、补偿和终态 | 引用步骤产生的 change_id | ORC，AUD 保存审计摘要 |
| AI Decision Log | 模型、知识版本、工具、用量和安全结果 | 引用消息或建议变化 | AIC，AUD 保存审计摘要 |
| Billing Log | 支付、额度、冲正和账单事件 | 对账单数据变化必须生成 Change | BIL/ENT，AUD 保存账本 |
| Operational Log | 健康、性能、积压、错误和资源状态 | 否 | 各模块运行系统 |

Data Change Ledger 是数据变化的唯一权威追踪来源。其他日志不得各自维护另一套“谁修改了对象”的最终结论。

## 4. 体系组件

| 组件 | 责任 |
|---|---|
| Change Registry | 登记所有允许改变数据的 Command、对象和预期动作 |
| Change Context | 在请求、Command、Event 和流程之间传递 actor、request、correlation 和 causation |
| Change Contract | 统一 change_id、对象版本、动作、Diff、敏感等级和合同版本 |
| Local Change Journal | 与业务变化同一原子边界保存 change_id、对象版本和待投递状态 |
| Change Publisher | 将未投递记录按顺序发送给 AUD，支持重试和检查点 |
| AUD Ingestion | 验证来源、合同版本、幂等和签名后接收 |
| Immutable Ledger | 只追加保存完整 Data Change Record |
| Audit Index | 为 Account、对象、操作者、时间、动作和流程建立查询索引 |
| Integrity Service | 计算记录摘要链、签名检查点和完整性结果 |
| Retention and Archive | 按数据分类执行热、温、冷存储和到期处理 |
| Audit API | 受控查询、对象时间线、导出和完整性验证 |
| Alert and Reconciliation | 发现高风险变化、投递积压、版本断层和账本缺口 |

## 5. 标准数据变更流程

1. 外部请求或内部流程产生 Command；
2. 权威模块验证身份、Account、权限、对象状态和字段；
3. 模块读取当前 object_version；
4. 计算将发生的业务变化和 changed_fields；
5. 在同一原子边界内保存业务数据和 Local Change Journal；
6. 返回新 object_version 和 change_id；
7. Change Publisher 将记录发送给 AUD；
8. AUD 按 change_id 幂等写入 Immutable Ledger；
9. AUD 更新查询索引和完整性摘要链；
10. 业务 Event、Webhook、报表和搜索引用同一 change_id/correlation_id；
11. 对账任务比较本地 journal 和集中账本；
12. 差异进入补发、纠正或高风险告警。

## 6. 原子性原则

| 场景 | 目标结果 |
|---|---|
| 业务变化成功、Local Journal 失败 | 整个业务变化失败，不允许无记录提交 |
| Local Journal 成功、集中 AUD 暂时不可用 | 业务可按策略成功，本地记录持续重试投递 |
| 集中 AUD 重复接收 | 按 change_id 返回已存在，不生成第二记录 |
| 集中 AUD 已写入、确认响应丢失 | 发布方重试，同一 change_id 保持幂等 |
| 业务校验失败且没有数据变化 | 不生成 Data Change；生成操作或安全失败记录 |
| 部分字段成功、部分字段失败 | 不允许模糊结果；要么原子失败，要么明确拆成多条变化 |
| 跨模块流程部分成功 | 每个模块记录自己的真实变化，ORC 记录流程终态和补偿 |

高风险模块可以在本地 Change Journal 无法可靠保存时拒绝数据写入。集中 AUD 暂时不可用时不应导致所有核心业务立即停止，但必须有本地持久记录、积压上限和告警。

## 7. 日志边界

### 7.1 必须进入 Data Change Ledger

- 创建、更新和删除；
- 状态、优先级、分配、已读位置和健康状态变化；
- 添加、移除、绑定、解绑和集合替换；
- Contact 合并、对象恢复和归档；
- 权限、角色、Feature、套餐、额度和安装配置变化；
- Token 撤销、Session 撤销和安全策略变化；
- Provider 授权、重授权、模板和连接状态变化；
- AI 模型、Assistant、知识索引、工具和额度记录变化；
- Plugin 安装、授权、停用和删除；
- 批量、导入、迁移和补偿实际改变的数据；
- 支付、退款、冲正和账号删除状态变化。

### 7.2 不生成 Data Change，但需要其他日志

- 无结果的查询；
- 参数校验失败；
- 权限拒绝；
- 登录失败；
- Provider 请求超时但尚未确认内部状态变化；
- 健康探测；
- 页面打开和普通浏览；
- 搜索未命中。

敏感查询、导出、查看审计、读取 Token 摘要等高风险读取必须生成 Access Log。

## 8. 数据所有权

- 业务模块拥有业务对象；
- Local Change Journal 属于业务变更原子机制，只保留投递和恢复所需期限；
- AUD 拥有集中不可变账本；
- Audit Index 是可重建索引，不是第二权威账本；
- RPT/SRH 只能消费 Change Event 建立投影；
- ORC 拥有流程步骤，但不拥有业务变化内容；
- API 只负责查询授权和字段视图；
- 插件只能获得 Scope 允许的日志摘要，不能读取完整账本。

## 9. LOG-01 实施步骤

1. 冻结 L0 Local Capture Plane 和 Central Ledger Plane 边界；
2. 冻结九类日志的用途和边界；
3. 确认 AUD 为 Data Change Ledger 唯一所有者；
4. 为26个模块登记 Change Context、Contract、Local Journal 和 Publisher 能力；
5. 区分数据变化、业务操作、安全、访问、投递和运行日志；
6. 确定 Local Capture 或集中 AUD 不可用时各模块的继续或拒绝策略；
7. 冻结 change_id、event_id、request_id 和 correlation_id 关系；
8. 建立 Change Registry；
9. 确定积压、告警和对账责任；
10. 检查日志体系没有成为第二业务数据库；
11. 完成基础层评审后进入 LOG-02。

## 10. 完成判定

- [ ] 九类日志边界清楚；
- [ ] 所有模块只依赖 L0 Local Capture Contract，不同步依赖 Audit API；
- [ ] Local Capture 不可用时没有任何业务写入绕过；
- [ ] Data Change Ledger 只有 AUD 一个权威所有者；
- [ ] 所有业务模块具备本地原子变更记录；
- [ ] 集中 AUD 故障不会造成无记录数据变化；
- [ ] 失败尝试和实际数据变化不会混淆；
- [ ] 跨模块流程可以通过 correlation_id 串联；
- [ ] 日志副本、索引和运行记录不会成为第二权威来源。
