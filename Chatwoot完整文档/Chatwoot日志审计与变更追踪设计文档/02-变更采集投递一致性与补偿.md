# 变更采集、投递、一致性与补偿

> 日志任务：LOG-03。

## 1. 目标

确保每一次已经提交的数据变化最终都进入 AUD，且不会因网络、重试、重启、重复投递或乱序产生缺失和重复账本。

## 2. Change Registry

每个允许写入数据的 Command 必须登记：

| 字段 | 内容 |
|---|---|
| command_type/version | 写动作和版本 |
| owner_module | 权威执行模块 |
| object_types | 可能变化的对象 |
| actions | create/update/delete 等 |
| expected_changed_fields | 允许变化字段范围 |
| actor_types | 允许来源 |
| requires_reason | 是否强制原因 |
| sensitivity | 数据分级 |
| retention_class | 保留类别 |
| atomicity | 单对象、多对象或流程步骤 |
| bulk_behavior | 批次和单对象记录方式 |
| failure_log | 失败时使用的日志类型 |
| alert_policy | 是否触发高风险告警 |

未登记 Command 不允许改变权威数据。

## 3. 单模块原子采集

1. 接收并验证 Command；
2. 读取当前对象和 object_version；
3. 计算真实差异；
4. 如果没有变化，返回 no_change，并可记录操作日志；
5. 生成 change_id、after_version 和 diff；
6. 在同一原子边界保存业务对象和 Local Change Journal；
7. Local Journal 标记 pending_delivery；
8. 提交成功后返回 change_id；
9. 异步 Publisher 读取 pending 记录；
10. AUD 确认后标记 delivered；
11. 本地记录超过保留期限后按确认状态清理。

业务对象和 Local Journal 不能分两次独立保存，否则中间失败会造成无法发现的审计缺口。

## 4. 多对象同模块变化

| 类型 | 记录方式 |
|---|---|
| 一个 Command 原子修改多个同模块对象 | 一个 parent_change + 每个对象 child_change |
| 集合关系替换 | 主对象一条 change，diff 记录 added/removed |
| 大批量逐条处理 | 一个 batch 记录 + 每对象独立 change |
| 状态变化同时更新时间 | 同一对象一条 change，联合记录状态和时间 |
| 创建主对象和内部子对象 | 按对象生命周期决定一条聚合 change 或多条关联 change |

## 5. 跨模块变化

跨模块不能使用同一个共享事务。采用以下方式：

1. ORC 创建 process_id/correlation_id；
2. 每个步骤向一个权威模块发送 Command；
3. 每个模块独立提交业务数据和自己的 Local Journal；
4. Change Record 共用 correlation_id，causation_id 指向上一步；
5. ORC 保存 step_id、command_id、change_id 和终态；
6. 后续步骤失败时执行显式补偿；
7. 补偿本身生成新的 change_id 并引用 original_change_id；
8. AUD 可以按 correlation_id 展示完整流程时间线。

不能因为流程最终失败就删除此前真实发生的变化记录。

## 6. 投递合同

| 字段 | 规则 |
|---|---|
| delivery_id | 每次投递尝试唯一 |
| change_id | 所有重试保持一致 |
| source_module | 与记录所有者一致 |
| source_sequence | 模块或分区内单调序号 |
| attempt | 从1开始递增 |
| payload_hash | AUD 验证重试内容没有变化 |
| sent_at | 投递时间 |
| acknowledged_at | AUD 确认时间 |
| status | pending、sent、acknowledged、retrying、dead_letter |
| error | 分类、重试时间和摘要 |

## 7. 幂等和顺序

- AUD 以 change_id 作为全局幂等键；
- 相同 change_id、相同 payload_hash 视为重复投递；
- 相同 change_id、不同 payload_hash 触发高风险完整性告警；
- 同一对象以 object_version 检查顺序；
- version 断层进入 pending_gap，不阻止其他对象写入；
- 旧版本晚到时保存接收事实但不改变时间线顺序；
- create 之前收到 update 必须等待缺失版本或进入修复队列；
- 跨对象不强求全局严格顺序，使用 occurred_at 和 correlation_id 还原流程。

## 8. 重试和死信

| 情况 | 处理 |
|---|---|
| AUD 暂时不可用 | 延迟重试并告警积压 |
| 认证或签名错误 | 停止自动重试，安全告警 |
| schema_version 不支持 | 进入隔离区，等待兼容处理 |
| payload_hash 冲突 | 高风险告警，不覆盖原记录 |
| Account 或模块信息缺失 | 进入修复队列 |
| 超过最大尝试 | 进入 dead_letter，保留原 Local Journal |
| 死信修复 | 使用同一 change_id 重新投递并记录修复人 |

## 9. 对账机制

### 9.1 数量对账

- 每模块、Account、时间分区的 committed changes；
- Local Journal delivered/pending/dead 数量；
- AUD 接收唯一 change_id 数量；
- object_type、action 和结果分布。

### 9.2 序列对账

- source_sequence 是否连续；
- object_version 是否从创建到当前连续；
- 是否存在 update 无 create、delete 后继续 update；
- 是否存在相同 change_id 不同摘要。

### 9.3 业务对账

- 当前对象版本是否等于最后一条 Change after_version；
- 对关键对象重放 Diff 是否能还原允许字段；
- 删除、合并和脱敏是否存在所有关联记录；
- ORC 步骤 change_id 是否全部能在 AUD 找到。

## 10. 集中 AUD 长时间不可用

| 阶段 | 行为 |
|---|---|
| 短时 | 本地持久积压，业务继续，立即告警 |
| 接近容量阈值 | 降低非核心批量和导入速度，扩大存储保护 |
| 达到高水位 | 暂停低优先级写入和高风险配置变化 |
| 达到安全上限 | 核心模块按政策进入只读或受限模式，禁止无记录写入 |
| AUD 恢复 | 按 source_sequence 补投、幂等接收、执行全量对账 |

每个模块必须定义本地积压容量、预警线、高水位和安全上限。

## 11. LOG-03 实施步骤

1. 建立 Change Registry，逐项登记所有同步、异步、回调、自动化、插件和迁移写入口；
2. 为每个权威模块确定 Local Change Journal 的原子边界、顺序分区和本地保留期；
3. 在所有写流程中统一生成 command_id、change_id、object_version 和 correlation_id；
4. 验证业务数据成功时本地记录必定成功，本地记录失败时业务数据不会提交；
5. 冻结 Publisher 的读取顺序、批量大小、确认、重试、退避和死信规则；
6. 冻结 AUD 接收端的来源认证、合同验证、payload_hash 和 change_id 幂等规则；
7. 验证响应丢失、重复投递、进程重启、消息乱序和集中账本中断；
8. 为多对象、批量和跨模块流程建立 parent、child、step 和 causation 关系；
9. 为可逆动作定义 compensate，为不可逆动作定义人工处置和风险终态；
10. 建立分钟、小时和日级的 committed、pending、delivered、ingested 对账；
11. 设置积压水位和写入降级顺序，先限制批量和低优先级动作；
12. 执行缺口补投、死信重放、版本断层处理和恢复后全量对账。
