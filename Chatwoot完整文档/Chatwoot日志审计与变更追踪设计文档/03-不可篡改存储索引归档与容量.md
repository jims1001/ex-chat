# 不可篡改存储、索引、归档与容量

> 日志任务：LOG-04。

## 1. 目标

集中账本必须只追加、可验证、可查询、可按保留政策归档，并能在高写入量下保持 Account 隔离和稳定性能。

## 2. 存储分层

| 层级 | 内容 | 目标 |
|---|---|---|
| Local Journal | 尚未确认投递和短期恢复记录 | 保证业务变化不丢失 |
| Hot Ledger | 最近高频查询的不可变记录 | 快速对象时间线和安全调查 |
| Warm Ledger | 较低频历史记录 | 账号审计和周期报表 |
| Cold Archive | 长期保留、低频访问的加密归档 | 合规、取证和灾难恢复 |
| Audit Index | Account、对象、操作者、时间和动作索引 | 快速定位，不作为权威内容 |
| Integrity Checkpoint | 分区摘要、签名和归档证明 | 检测删除、插入和修改 |

## 3. 分区设计

建议至少按以下维度组合分区：

- account_scope；
- occurred_at 时间窗口；
- source_module；
- retention_class；
- 必要时 object_type。

分区必须支持：

- 单 Account 数据隔离和导出；
- 按时间归档和保留；
- 大 Account 独立扩展；
- 完整性摘要链范围可控；
- 读取热点不会影响其他 Account；
- 平台级记录与普通 Account 记录明确分离。

## 4. 不可变规则

- Ledger 只允许 append；
- 普通业务身份没有 update 和 delete 能力；
- 日志描述错误通过 correct_log 追加；
- 合法到期清理由专用保留流程执行；
- 清理前生成分区清单、数量、时间范围和摘要；
- 清理后生成 purge certificate；
- 归档对象有完整性摘要和签名；
- 恢复归档时验证摘要后才允许查询；
- AUD 自身配置变化也必须被另一个受控审计范围记录。

## 5. 防篡改设计

### 5.1 摘要链

每条记录的 integrity_hash 由以下内容计算：

- 规范化后的记录内容；
- previous_hash；
- 分区标识；
- schema_version；
- source_module 和 change_id。

同一分区形成连续摘要链。修改、删除或插入历史记录都会造成后续验证失败。

### 5.2 签名检查点

- 每个固定时间窗口生成 checkpoint；
- checkpoint 包含首尾 change_id、记录数和根摘要；
- 使用独立密钥签名；
- 签名密钥与业务模块和普通 AUD 查询权限分离；
- checkpoint 复制到独立保留位置；
- 每日或按风险级别验证；
- 验证失败立即进入安全事件。

### 5.3 管理职责分离

| 权限 | 不能同时拥有的能力 |
|---|---|
| 日志查询 | 不能修改保留和签名策略 |
| 日志导出 | 不能删除归档 |
| 保留管理 | 不能查看所有敏感 before/after |
| 完整性验证 | 不能重新生成历史业务记录 |
| 密钥管理 | 不能普通查询业务日志 |

## 6. 索引设计

| 索引 | 用途 |
|---|---|
| account_id + occurred_at | Account 时间线 |
| object_type + object_id + object_version | 对象完整变化历史 |
| actor_type + actor_id + occurred_at | 操作者行为调查 |
| action + occurred_at | 删除、权限、配置等高风险变化 |
| correlation_id | 跨模块流程时间线 |
| request_id/command_id | 从请求定位业务变化 |
| source_module + source_sequence | 投递完整性和断层检查 |
| event_id | 业务事件与变化关联 |
| source_type/source_id | 插件、规则、迁移或 Provider 来源 |
| data_classification + retention_class | 权限过滤和保留任务 |

全文搜索不能默认索引受限原值。敏感内容应使用受控摘要、脱敏值或权限隔离索引。

## 7. 热温冷迁移

1. 记录先进入 Hot Ledger；
2. 超过热数据周期且无调查锁定后进入 Warm；
3. 超过常用查询周期后打包进入 Cold Archive；
4. 迁移前后比较记录数、首尾 ID、摘要和 checkpoint；
5. 归档确认后才允许释放前一层副本；
6. 查询冷数据先提交授权请求和解档任务；
7. 解档结果有有效期并自动清理；
8. 法律保留中的记录不得按普通周期清理。

## 8. 容量估算维度

- 每日数据变更次数；
- 每条 diff 平均字段数和大小；
- 消息、导入、自动化和 Provider 回调峰值；
- 最大 Account 占比；
- Hot/Warm/Cold 保留天数；
- 索引膨胀比例；
- 摘要和签名检查点开销；
- 批量和迁移临时峰值；
- 重试与本地积压上限；
- 合规导出并发量。

容量不足不能通过丢弃 Data Change Record 解决，应采用分区、归档、限流和降低非必要 before/after 详细度。

## 9. 查询性能与写入隔离

- Ledger 写入和复杂查询使用独立容量；
- 大导出使用异步任务和快照范围；
- 单 Account 大查询不能占满全局查询资源；
- 对象时间线优先使用固定索引；
- 任意全文查询必须有时间和 Account 边界；
- Cold Archive 解档不阻塞 Hot 写入；
- 索引损坏可以从 Ledger 重建；
- Ledger 不因索引失败而回滚已确认记录。

## 10. 灾难恢复

1. 定期保存不可变账本备份和 checkpoint；
2. 恢复到隔离环境；
3. 验证签名、摘要链、记录数和时间范围；
4. 恢复索引而不是信任旧索引；
5. 比较各模块 Local Journal 最后确认位置；
6. 补投缺失 change_id；
7. 对重复记录幂等处理；
8. 生成恢复差异报告；
9. 全部差异关闭后恢复正式查询。

## 11. LOG-04 实施步骤

1. 按 Account、时间、来源模块和数据位置要求冻结账本分区策略；
2. 为每条记录生成规范摘要，并建立分区内 previous_hash 链；
3. 确定 checkpoint 周期、签名权限、密钥轮换、验证和异常隔离规则；
4. 建立只追加权限模型，禁止普通更新、覆盖和直接删除；
5. 建立按 Account、对象、操作者、动作、时间和 correlation_id 的可重建索引；
6. 冻结 Hot、Warm、Cold 的进入条件、查询时延、保留和恢复目标；
7. 按对象变化量、Diff 大小、索引倍数、保留周期和增长峰值估算容量；
8. 设置写入容量、归档积压、索引延迟和存储水位告警；
9. 验证大范围查询、导出和索引重建不会阻塞 Ledger 写入；
10. 验证备份恢复后记录数量、首尾摘要、checkpoint 和对象时间线一致；
11. 执行记录篡改、缺失、插入、重排和重复的完整性检测；
12. 形成扩容、跨区恢复、冷数据解档和灾难恢复验收证据。

- [ ] 管理权限完成职责分离；

- [ ] 容量规划覆盖峰值、积压和大 Account；
