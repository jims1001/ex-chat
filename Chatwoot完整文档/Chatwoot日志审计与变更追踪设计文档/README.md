# Chatwoot 日志基础层、审计与数据变更追踪设计文档

> 目标：把日志设计成全系统 L0 基础层，使每一次业务数据变化都留下完整、可查询、可关联、可验证且不可静默修改的记录，同时避免日志系统成为第二套业务数据库。

本目录是 [全系统基础层规范](../Chatwoot全系统基础层规范/README.md) 中数据完整性、变更追踪、安全和可靠性规则的专项展开。若专项内容与基础层总纲冲突，先修订冲突并重新打开相关 LOG 任务，不能由日志分册自行建立例外。

## 1. 强制要求

1. 所有模块必须依赖统一日志基础合同，任何绕过基础层的写入都不允许发布；
2. 所有创建、修改、状态变化、绑定、解绑、合并、删除、恢复、导入、迁移和批量操作都必须生成 Data Change Record；
3. 业务数据变化与本地变更记录必须原子完成，不能出现“数据已经改变但没有记录”；
4. AUD 是集中审计与变更账本的唯一所有者；
5. 各业务模块只保留待投递记录和必要短期副本，不能建立第二套永久审计账本；
6. 变更记录只追加，不允许覆盖、回写或静默删除；
7. 每条记录必须包含 Account、对象、版本、操作者、来源、前后差异、时间和因果链；
8. 密码、Token、Secret、MFA 信息和完整支付凭证绝不能写入日志；
9. 跨模块流程必须使用 correlation_id 连接所有步骤；
10. 批量操作既要记录批次，也要记录每个实际变化对象；
11. 每个模块上线前必须证明其所有数据写动作已经进入变更覆盖矩阵。

## 3. 实施位置

日志体系属于 L0 基础层，但不新增第二个业务所有者：

- 业务模块仍拥有自己的对象和状态；
- 所有模块只依赖 L0 Change Contract、Context、Local Journal 和 Publisher，不同步依赖集中查询服务；
- 业务模块在改变对象时生成原子变更记录；
- AUD 接收并保存不可变账本；
- API 提供受控查询和导出；
- ORC 为跨模块流程提供关联标识；
- RPT 可以消费日志统计完整性，但不能把报表当作审计账本；
- SRH 可以建立日志搜索索引，但索引不是权威记录。

## 4. AI 执行顺序

1. 完成模块化架构 ARCH-01 至 ARCH-10；
2. 完成基础版本和范围 BAS-01 至 BAS-12；
3. 完成 LOG-01 至 LOG-08；
4. 只有日志体系通过后，公共接口和业务功能任务才能开始；
5. 每个后续业务任务都要在 LOG-08 矩阵中登记写动作；
6. 新增字段、状态或模块时，必须重新打开受影响的 LOG 任务。

## 5. 完成定义

- 26 个模块的全部权威写动作已登记；
- 所有模块接入同一 L0 日志基础合同；
- 每次成功数据变化都有唯一 change_id；
- 数据未变化的失败尝试进入安全或操作日志，但不伪造 Data Change；
- 创建、更新、删除、合并、批量、导入和迁移均可追踪；
- 本地待投递记录与 AUD 集中账本最终一致；
- 日志记录不可静默修改，修正只能追加纠正记录；
- 敏感字段从未以原值进入日志；
- 查询、导出和查看日志本身也受权限控制并被审计；
- 日志积压、丢失、重复、乱序和恢复均经过验证；
- 未记录的数据变化数量为 0。
