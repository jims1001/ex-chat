# 跨模块流程编排规则

> 架构任务：ARCH-07。跨模块流程必须有一个明确编排者，业务模块不能通过互相回调形成循环。

## 1. ORC 的职责

ORC 只管理：

- 流程类型和合同版本；
- process_id、correlation_id 和因果链；
- 步骤顺序、等待条件和超时；
- 每步 Command、目标模块和幂等键；
- 步骤成功、失败、重试、跳过和人工接管；
- 补偿动作和补偿终态；
- 流程结果摘要。

ORC 不保存客户、会话、消息、分配、支付、知识等领域对象正文，也不重新实现它们的业务规则。

## 2. 需要编排的判断

满足以下任一条件应使用 ORC：

- 一个业务目标需要两个以上模块改变状态；
- 不能使用单个共享事务保证完成；
- 存在外部 Provider、异步任务或人工确认；
- 失败时需要跨模块补偿；
- 流程可能持续数分钟、数天或更长；
- 需要在系统重启后继续；
- 需要向外提供整体进度和终态。

纯单模块动作不应经过复杂编排，直接调用所有者 Command。

## 3. 编排状态

| 状态 | 含义 |
|---|---|
| created | 流程已建立，尚未执行 |
| running | 正在执行可运行步骤 |
| waiting | 等待事件、时间、外部回执或人工输入 |
| compensating | 正在执行已完成步骤的补偿 |
| completed | 业务目标全部完成 |
| partially_completed | 允许保留的部分结果完成，差异已明确 |
| failed | 无法继续且补偿已结束 |
| cancelled | 按请求停止，未执行步骤不会开始 |
| manual_action_required | 需要授权、判断或外部修复 |

## 4. 通用编排规则

1. 每个流程只有一个 ORC 实例作为协调权威；
2. 每步只调用模块公开 Command；
3. 每步使用稳定幂等键；
4. Command 超时后先 Query 结果；
5. 模块以 Event 或 Process Signal 报告最终结果；
6. ORC 不要求模块反向调用 ORC 的内部状态；
7. 可并行步骤必须没有相互状态依赖；
8. 失败策略在流程启动前冻结；
9. 补偿不是数据库回滚，而是新的显式业务动作；
10. 不可逆步骤执行前必须完成必要检查和确认；
11. 流程更新使用版本，防止两个执行者同时推进；
12. 所有步骤、错误和补偿进入 AUD。

## 5. 入站消息流程

| 顺序 | 模块 | 动作 | 失败处理 |
|---:|---|---|---|
| 1 | API/EXT | 验签、定位 ChannelConnection、Callback 去重 | 无效回调拒绝；重复返回既有结果 |
| 2 | CHN | 确认 Inbox、Provider 能力和健康 | 连接无效时记录并停止 |
| 3 | CUS | 按 Inbox + source_id 创建或查找 ContactInbox | 冲突进入人工或确定合并规则 |
| 4 | CON | 查找或创建目标 Conversation | 并发创建按幂等规则收敛 |
| 5 | MED | 获取或登记媒体资源 | 媒体失败可生成明确失败附件或补偿 |
| 6 | MSG | 创建 incoming Message | external_id 去重；主消息成功后不因副作用回滚 |
| 7 | RTE | 必要时入队和分配 | 无候选保持排队，不删除消息 |
| 8 | AUT/AIC | 消费事件执行规则或 AI | 失败独立记录，可转人工 |
| 9 | NTF/RTM/EXT/RPT/SRH/AUD | 消费事实形成投递和投影 | 各自重试，不反向回滚 MSG |

## 6. 出站消息流程

1. API 验证身份和接口合同；
2. ORC 取得 CON、CHN 和权限状态；
3. MSG 创建 pending Message，并以 message_id 作为发送幂等标识；
4. MED 提供有效附件读取授权；
5. CHN/Channel Adapter 提交 Provider；
6. MSG 保存外部 ID 和 accepted/sent 状态；
7. Provider Callback 更新 delivered/read/failed；
8. 超时后按外部 ID 查询或等待回调；
9. NTF、RTM、EXT、RPT、SRH、AUD 消费消息事实；
10. 最终发送失败可以重试，但复用同一业务幂等关系。

MSG 成功保存后，Webhook 或通知失败不能删除该消息。

## 7. 自动分配流程

1. CON 发布 conversation.created 或可分配状态变化；
2. RTE 验证 Inbox 策略、成员、availability 和容量；
3. RTE 原子选择候选并占用容量；
4. RTE 发布 assignment.changed；
5. API 通过 CON Query 与 RTE Query 聚合展示；CON 不保存第二份分配权威状态；
6. NTF 生成分配通知；
7. RPT、SRH 和 AUD 消费分配事件形成投影或记录；
8. 并发失败时 RTE 重新计算，不由 CON 覆盖分配。

分配事实只由 RTE 拥有，避免 CON 与 RTE 双向同步形成环。

## 8. Automation 流程

1. 业务所有者发布事实事件；
2. AUT 以 event_id + rule_id + version 建立执行幂等键；
3. AUT 读取公开 Query 判断条件；
4. 动作由 AUT 向目标模块发 Command，或启动 ORC 子流程；
5. 目标模块执行自己的权限和业务规则；
6. AUT 记录每个动作结果；
7. 新事件保留 causation_id 和递归深度；
8. 超过深度、重复因果链或互相触发时停止；
9. 业务模块从不反向依赖 AUT。

## 9. AI 回答流程

1. MSG/CON 事实触发 AI 资格判断；
2. AIC 检查 ENT、模型、Assistant、额度和 Inbox Binding；
3. AIC 通过 KB Query 获取指定版本知识；
4. AIC 通过 CON/MSG Query 获取授权上下文；
5. Tool 调用通过 EXT/ORC 和目标 Capability；
6. 生成回答后执行安全检查；
7. 自动回复时由 ORC 调用 MSG 出站流程，建议模式只写 Copilot；
8. ENT 记录用量，RPT/AUD 消费事实；
9. 失败按回退模型、转人工或明确失败处理；
10. CON 和 MSG 不反向依赖 AIC。

## 10. Campaign 流程

1. OPS 冻结受众和逐目标记录；
2. ORC 按计划时间启动发送批次；
3. 对每个目标重新检查 ENT、CHN、退订和客户状态；
4. 调用 MSG 出站流程；
5. MSG 最终状态回流为 CampaignRecipient 结果；
6. OPS 汇总活动状态；
7. 暂停只停止未开始目标；
8. 重启不重复已受理 message_id；
9. RPT/AUD 只读消费结果。

## 11. Account 删除流程

1. TEN 接受删除请求并进入 scheduled 状态；
2. ORC 等待可取消窗口；
3. 检查 BIL、ENT、MIG 和法律保留条件；
4. IAM 撤销相关业务访问；
5. 各数据所有者执行删除、脱敏或保留；
6. EXT 撤销插件和 Provider 授权；
7. SRH、RPT、AIC、NTF、RTM 清理投影和订阅；
8. AUD 按政策保留必要记录；
9. ORC 核对全部步骤；
10. TEN 进入 deletion_completed；
11. 任一步失败进入补偿或人工处理，不能提前声明完成。

## 12. 导入和迁移流程

1. MIG 验证来源、字段映射、唯一和范围；
2. 为每批记录建立检查点；
3. 按对象依赖顺序调用各所有者 Command；
4. 目标模块执行与在线入口相同规则；
5. MIG 保存 legacy_id → target_id；
6. 失败行独立记录，成功行不重复；
7. 中断后从检查点继续；
8. 完成后执行数量、关系、内容和权限对账；
9. 回退通过显式补偿批次，不直接删除目标内部数据。

## 13. 补偿原则

| 已完成动作 | 允许补偿 | 不允许的假回滚 |
|---|---|---|
| 创建临时会话但未产生消息 | 按 CON 生命周期取消或归档 | 直接删除内部记录 |
| 消息已被客户收到 | 记录失败后续动作或发送纠正消息 | 假装消息从未发送 |
| 已占用容量 | RTE 释放 Assignment | CON 修改容量数字 |
| 已生成支付 | BIL 退款或冲正 | ENT 直接删除支付事实 |
| 已安装插件 | EXT 停用、撤权和清理 | 只隐藏页面但保留有效 Token |
| 已导入对象 | MIG 调用对象所有者的删除/归档 Command | MIG 直接删除目标存储 |
