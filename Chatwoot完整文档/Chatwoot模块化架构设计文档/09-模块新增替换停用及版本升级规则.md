# 模块新增、替换、停用及版本升级规则

> 架构任务：ARCH-10。模块生命周期变化不能破坏所有权、无环依赖、接口兼容和历史数据。

## 1. 变更类型

| 类型 | 说明 | 必须重新检查 |
|---|---|---|
| 新增模块 | 引入新的独立业务领域或能力 | 边界、所有权、依赖、接口、插件、验收 |
| 扩展模块 | 在现有职责内增加对象、动作或事件 | 所有权、合同版本、重复检查 |
| 拆分模块 | 一个模块拆为两个或多个 | 数据迁移、依赖方向、双主写、流程编排 |
| 合并模块 | 多个模块合为一个 | 职责是否过宽、独立能力和退役合同 |
| 替换模块 | 新实现接管同一合同和数据所有权 | 双运行、对账、切换和回退 |
| 停用模块 | 暂时关闭功能 | 降级、积压、恢复和客户提示 |
| 退役模块 | 永久停止并移除合同 | 使用方清零、数据处置、审计和兼容结束 |
| 升级模块 | 版本、合同或数据结构变化 | 兼容、灰度、回退和事件版本 |

## 2. 新增模块准入

新增模块必须回答：

1. 新能力为什么不能归入现有模块；
2. 唯一职责是什么；
3. 明确不负责什么；
4. 拥有哪些对象、状态、配置和凭证；
5. 依赖哪些模块，是否违反层级；
6. 提供哪些 Command、Query、Event；
7. 是否需要 ORC 编排；
8. 是否提供插件扩展点或对外接口；
9. 停用后系统如何降级；
10. 独立存储、扩缩、升级和恢复如何验证；
11. 是否引入重复功能或数据；
12. 谁负责版本、证据和退役。

任一问题没有明确答案时，不能进入功能实施。

## 3. 模块替换流程

### 3.1 准备

1. 冻结旧模块公开合同、数据所有权和当前业务行为；
2. 新模块实现同一合同或提供明确兼容转换；
3. 建立权威数据迁移和 stable ID 方案；
4. 确定单一主写者；
5. 准备请求、事件、数据和业务结果对账；
6. 准备回退点和切换后增量数据处理。

### 3.2 双运行

- 旧模块保持唯一主写；
- 新模块接收镜像 Query、Command 影子输入或 Event；
- 新模块结果不能产生真实外部副作用；
- 比较状态、错误、事件、性能和资源使用；
- 差异进入明确分类；
- 不允许两个模块同时发布同一权威事件。

### 3.3 切换

1. 完成全量数据和增量同步；
2. 将小范围 Account 或流量切到新模块主写；
3. 旧模块进入只读或影子验证；
4. 核对 Command、Query、Event 和外部副作用；
5. 扩大灰度范围；
6. 达到关门条件后全量切换；
7. 保留旧模块只读和回退能力到观察期结束。

### 3.4 回退

- 停止新模块接受新主写；
- 处理切换后新增事实和外部副作用；
- 将可回迁数据按 stable ID 同步回旧模块；
- 恢复旧模块主写；
- 重新发布或补读必要事件但不重复副作用；
- 对无法回退的事实明确人工处理；
- 保存完整回退审计。

## 4. 模块停用规则

| 模块类型 | 停用要求 |
|---|---|
| 核心模块 | 只能进入维护模式或由兼容模块接管，不允许无替代关闭 |
| 可选业务模块 | 阻止新动作，完成或暂停运行任务，核心流程继续 |
| 投影模块 | 标记数据陈旧，保留权威查询降级，恢复后补读 |
| 外部连接模块 | 撤销或暂停授权，保留内部事实，恢复后检查回调缺口 |
| 商业模块 | 冻结新购买，不能擅自撤销已生效权益 |
| 审计模块 | 高风险动作可保守暂停，不能无记录继续敏感操作 |

停用必须包含：原因、开始时间、影响范围、用户可见提示、运行任务处理、数据保留、恢复条件和最长持续时间。

## 5. 模块退役规则

1. 所有调用方和事件订阅方清零；
2. 所有插件和外部接口完成迁移；
3. 权威数据已迁移、导出、保留或删除；
4. stable ID 和历史链接仍可解释；
5. 运行中任务和回调已收口；
6. Secret 和第三方授权已撤销；
7. 旧合同经过公告和兼容期；
8. 搜索、报表、AI 和审计副本按政策处理；
9. 回退窗口结束并取得批准；
10. 移除后重新执行无环和重复检查。

## 6. 版本类型

| 版本 | 适用内容 | 兼容要求 |
|---|---|---|
| module_version | 模块整体发布版本 | 不直接决定接口兼容 |
| command_version | 写动作合同 | 旧调用方在兼容期仍可工作 |
| query_version | 查询字段和语义 | 新增字段兼容，删除或改义提高主版本 |
| event_version | 事实 Payload | 订阅方可同时消费迁移期版本 |
| data_version | 权威数据格式 | 支持滚动升级和回退读取 |
| plugin_contract_version | 插件扩展点 | 插件兼容范围清楚 |
| external_api_version | 对外接口族 | 与内部模块版本解耦 |
| process_version | ORC 流程步骤 | 运行中流程继续使用启动时版本 |

## 7. 兼容变化与破坏性变化

### 7.1 通常兼容

- 响应或 Event 新增可选字段；
- 新增可选 Command 输入并有默认行为；
- 新增错误详情但错误类别不变；
- 新增 Query 筛选和排序；
- 新增独立事件类型；
- 性能和内部实现变化但业务合同不变。

### 7.2 破坏性变化

- 删除字段或改变字段含义、单位、可空性；
- 改变对象 ID 或唯一范围；
- 改变 Command 幂等或副作用；
- 改变状态转换和终态；
- 改变身份、权限或 Scope；
- 改变事件发布时机和事实含义；
- 改变错误类别导致重试策略变化；
- 改变数据所有者；
- 改变模块依赖方向。

破坏性变化必须使用新合同版本、迁移计划、双运行或兼容层。

## 8. 升级顺序

1. 先发布使用方能够理解的新合同定义；
2. 提供方同时支持旧版和新版；
3. 逐个迁移使用方；
4. 验证旧版和新版进入同一业务所有者；
5. 观察错误、事件、数据和副作用；
6. 停止新增旧版使用方；
7. 到达公告期限后关闭旧版写入；
8. 保留必要只读和历史解释；
9. 确认使用方为 0 后移除旧版；
10. 更新依赖、插件、对外接口和证据。

## 9. 变更审批门

| 门 | 必须通过的内容 |
|---|---|
| D1 边界 | 新职责不与现有模块重叠 |
| D2 所有权 | 对象和状态只有一个所有者 |
| D3 依赖 | 拓扑排序成功，无同步和事件环 |
| D4 合同 | Command、Query、Event 和错误版本完整 |
| D5 扩展 | 插件和对外入口兼容 |
| D6 数据 | 迁移、双主写防护、对账和回退完整 |
| D7 运行 | 独立启停、故障、扩缩和恢复通过 |
| D8 业务 | 核心流程、历史兼容和既有能力无回退 |
| D9 观察 | 指标、追踪、审计和证据完整 |
| D10 收口 | 旧使用方、旧事件和旧数据处理完毕 |

## 10. ARCH-10 完成判定

- [ ] 新增、扩展、拆分、合并、替换、停用、退役和升级均有规则；
- [ ] 模块替换不存在两个主写者或重复权威事件；
- [ ] 停用和退役有运行任务、数据、Secret 和外部回调处理；
- [ ] 八类版本相互独立且可追踪；
- [ ] 破坏性变化均有新版本和迁移方案；
- [ ] 升级支持灰度、观察和回退；
- [ ] 变更后重新执行边界、所有权、无环和重复检查；
- [ ] D1 至 D10 全部通过后才允许发布。
