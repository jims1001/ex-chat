# Chatwoot 与 webchat 模块化架构设计文档

> 目标：把完整客服系统划分为职责单一、数据归属唯一、依赖单向、可独立替换、可独立运行、可通过插件扩展且可安全对外开放的模块体系。

本目录是 [全系统基础层规范](../Chatwoot全系统基础层规范/README.md) 的模块化专项展开。模块边界、依赖和扩展设计必须先遵守基础层 00 至 10；本目录不能建立与基础层冲突的公共合同。

## 1. 强制原则

1. 一个业务能力只能有一个权威归属模块；
2. 一个业务对象只能有一个权威数据源；
3. 模块之间只能通过已登记的接口、事件或流程编排协作；
4. 禁止直接读取或修改其他模块的内部存储；
5. 同步依赖和事件依赖都必须单向，完整依赖图必须无环；
6. 跨模块业务由流程编排模块负责，业务模块不得相互回调形成闭环；
7. 搜索、报表和缓存只能保存可重建副本；AUD 可以拥有不可变变更账本，但不能成为业务对象事实来源；
8. 插件只能使用公开扩展点和授权能力，不能进入模块内部；
9. 对外接口不能绕过模块合同直接操作数据；
10. 每个模块都必须通过独立启停、独立升级、依赖故障和数据归属验收。

## 3. AI 阅读和执行顺序

AI 在实施任何业务功能前必须：

1. 阅读 [全系统基础层规范 00 至 10](../Chatwoot全系统基础层规范/README.md)；
2. 阅读本目录 00 至 10；
3. 完成 ARCH-01 至 ARCH-10；
4. 在 [AI 全任务状态记录](../Chatwoot-AI实施步骤文档/28-AI全任务状态记录.md) 登记结果；
5. 确认模块边界、所有权和依赖图已经冻结；
6. 再进入 [AI 实施步骤文档](../Chatwoot-AI实施步骤文档/README.md) 的 BAS 和后续功能任务。

ARCH 完成并冻结目标基线后，必须先完成 [日志基础层、审计与数据变更追踪设计](../Chatwoot日志审计与变更追踪设计文档/README.md) 的 LOG-01 至 LOG-08，再开始公共接口和业务写任务。日志作为 L0 基础合同运行，不改变业务对象的数据所有权，也不允许业务模块同步依赖集中日志查询。

任何功能任务发现需要跨模块共享数据、反向调用或建立第二权威来源时，必须停止该任务，重新打开对应 ARCH 任务，不能以临时复制或直接访问绕过架构约束。

## 4. 完成定义

模块化架构只有在以下条件全部满足时才完成：

- 26 个模块均有明确职责和禁止边界；
- 所有主要业务对象只有一个权威所有者；
- 直接依赖表和分层矩阵不存在环；
- 模块间 Command、Query、Event 均有稳定合同；
- 插件扩展点、权限、生命周期和隔离规则完整；
- 对外入口只能进入应用接口层；
- 关键跨模块流程有唯一编排者和补偿规则；
- 每个可选模块关闭时核心客服仍能运行；
- 重复功能和重复数据检查没有未解释项；
- 新增、替换、停用和升级有兼容及回退方案。
- 26 个模块均使用 L0 Local Capture Contract，每个数据变化与本地变更记录原子提交；
- 集中审计账本只追加、可验证、可补投，并且不形成第二业务数据源。
- 默认组合部署保持简单实用，按容量、安全和故障边界可以拆分；
- 自动化与宏复用统一 Action Capability，不复制业务动作；
- 所有模块、流程和业务结果可跟踪、可量化；
- 合并部署与拆分部署的功能、权限、事件和数据结果一致。
